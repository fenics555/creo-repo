## Ключевые факты, которые направление уже добыло

1. **Версия 0.34.1.** Эндпоинта `/api/tokenize` нет (404 на GET и POST) — единственный
   измеритель токенов `prompt_eval_count`, и он врёт на переполнении окна (4099 на любом
   входе длиннее ~21 тыс. символов).
2. **`think` — строка с уровнем:** `true/false/high/medium/low`. Дом долго умел только булев.
3. **`OLLAMA_LOAD_TIMEOUT` = 5m** — кандидат на причину молчаливых обрывов прогонов на
   моделях 10-15 ГБ. Разбор не проводился.
4. **`OLLAMA_MAX_LOADED_MODELS=1` в доме** — любая проверка вытесняет рабочую модель.
5. **Стенд ходит в HTTP-API напрямую**, а не через CLI. Справка CLI про API не пишет ничего —
   по API нужен `ollama.com/docs`.

## ОТКРЫТАЯ ГИПОТЕЗА H-TEMPLATE: правила можно регулировать через Modelfile (слово владельца)

**Слово владельца 02.10.2026:** «можно с помощью его шаблона отрегулировать правила».
Смысл правила записан, потому что работа фазы большая, а гипотеза может дать ещё слой.

**Что установлено живой проверкой `ollama show gemma4:26b --modelfile` (ФАКТ):**
1. `TEMPLATE {{ .Prompt }}` — **пустой passthrough**: модель получает ровно то, что отправили.
   Никакой своей обёртки диалога у моделей дома нет.
2. `SYSTEM` — **0 строк**: своего системного промпта у моделей нет вовсе.
3. **Рычаг уже построен:** `tools\Apply-AgentParams.ps1` имеет ключ `-SystemPrompt`, который
   внедряет `SYSTEM` из `config\behavior.md`, а в `config\behavior.json` стоит
   `"systemPrompt": {"enabled": false, "file": "behavior.md"}` — то есть **механизм готов и
   выключен**.

**Что уже измерено про действующий способ.** Правила приходят через system prompt от клиента
и дают разницу: gemma4:26b `plain` 6/15 против `house` 15/15 — **+9 баллов**. То есть нынешний
канал работает, и вопрос не «работает ли», а «лучше ли второй канал».

**Гипотеза H-TEMPLATE:** перенос части правил из system prompt клиента в `SYSTEM` модели
(или в `TEMPLATE`) даст другой результат — на тех же правилах.

**Условия проверки (иначе это будет не замер, а правка наугад):**
1. **Сначала эталон на текущем канале** — уже есть: `house` ck5 из базы выше.
2. **Включать только на изолированной копии одной модели**, не на стеке: перезапись
   пересобирает модель на месте (`Apply-AgentParams.ps1` пересоздаёт тот же тег).
3. **Не смешивать каналы молча.** Если правила остаются в system prompt клиента И добавлены
   в `SYSTEM` модели — это **двойная подача**, а дом уже мерял обратный эффект: избыток текста
   роняет слабую модель (`SKILL_full_block_noise_for_weak_model.md`, laguna 9→4).
4. **Условие приёмки — как у любой правки правил:** `chars=`, `sha256=`, весь стек или минимум
   контрольная тройка 26b / glm / laguna-xs-2.1 (слабейшая по запасу в окне).
5. **Что может не сработать и это надо честно проверить:** стенд шлёт свои правила сам, поэтому
   при включённом `SYSTEM` вход всех замеров меняется — старые числа базы станут несопоставимы
   (см. закон о разных шкалах в `SKILL_answer_vs_thinking.md` §6).
6. **Скрипт сохраняет `TEMPLATE` и `FROM` как есть** — значит правка `SYSTEM` переживёт
   переприменение параметров, но добавить её надо в сам скрипт, иначе следующая пересборка
   модели её не заметит.

**Статус: НЕ ПРОВЕРЕНО.** Пока это записанная мысль с условиями, а не результат.
Очередь оптимизации правил исчерпана (H1-H7 закрыты) — это гипотеза **следующего** круга,
а не текущей фазы.

## Грабли направления (кратко; полные — в телах скиллов)

- Мерить размышление вместо ответа (подмена полей) — метрологическая ошибка, стоившая
  gpt-oss трёх баллов и целой группы в отчёте.
- Поднимать `num_predict` всем: laguna-xs.2 при 2000 генерирует 2000 токенов мусора вместо
  60 — время прогона растёт, качество не меняется.
- Опрашивать длинный прогон каждые 25 с — петля (`crash_sleep-poll-loop-after-timeout`, повтор 2).
- Оценивать время прогона «на глаз» — факт двух моделей на том же лимите даёт точную оценку.
