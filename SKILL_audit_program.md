# АУДИТ ПРОГРАММЫ (не дома)

Двойник `SKILL_audit_protocol.md`, но предмет — **одна программа** (`D:\AI\tools\agent\<имя>`),
а не дом. Здесь — **принципы**, а не жёсткий список: у каждой программы своя специфика
(одна пишет в базу, другая — в отчёты, третья — в ini), поэтому список «что проверять»
задаёт проверяющий, а не скилл.

== 0. СУТЬ АУДИТА ПРОГРАММЫ (три вопроса) ==

1. **Одна ли база?** Данные лежат в одном месте или разъехались: копии, «активная + старая»,
   база в папке программы И в общей папке, файл на диске D и копия на Z.
2. **Одни ли настройки?** Один источник значений — или значения зашиты в код, и при этом
   ещё дублируются в окне, в CLI и в визарде (три ручки — три разных места = будут расходиться).
3. **Нет ли лишнего?** Мусор: устаревшие копии и логи, временные файлы, legacy-дубли,
   `__pycache__`, пробы, урна, старые бэкапы сверх нужного.

Если по трём пунктам чисто — программа в порядке, остальное детали.

== 1. КАК ИСКАТЬ (своими средствами, не по шаблону) ==

* **Где пишет:** искать в коде создание папок/файлов (`makedirs`, `open(..., 'w'/'a')`,
  `copy`, `move`, `remove`), константы с путями, переменные окружения (`os.environ.get`),
  файлы, которые появляются после первого запуска.
* **Откуда читает:** те же места + `--help` программы, + её собственный вывод о путях.
* **Проверка «одна база / одни настройки»:** найти ВСЕ места, откуда берётся каждое значение
  (папки, пороги, столбцы, имена параметров), и убедиться, что источник один.
  Обычно второй источник — константа в коде или значение по умолчанию, которое никто не видит.

== 2. ЧТО ПРОВЕРЯТЬ ЖИВЫМ ВЫЗОВОМ ==

* **Каждая ручка:** команда командной строки (код возврата + осмысленность вывода) и
  каждая важная кнопка окна — открыть и посмотреть (хотя бы одна-две вживую).
* **Окно:** стартует ли, видна ли главная панель, не сыпет ли `stderr`, совпадает ли шапка
  версии с манифестом обновления.
* **Данные:** если база — `PRAGMA integrity_check` (sqlite) и счётчики; если файл — что он
  открывается и читается.
* **Логи:** куда пишет, что в хвосте, есть ли ошибки.
* **Паспорт:** README и паспорт программы — сверь с диском: файлы, команды, числа.

== 3. ТЯЖЁЛОЕ — ПО ФАКТУ, А НЕ ПО СПИСКУ ==

Признак тяжёлого запуска — **измеримый**, а не заранее воображаемый: команда идёт
заметно дольше обычной (минуты) ИЛИ обходит весь склад/весь диск целиком.
Как узнать: проба с ограничением (узкая папка, `--limit`, малая глубина) + замер времени.
**Не знаешь, что тяжёлое, — не называй тяжёлым.** Либо ограничь пробу, либо спроси после замера.
Ограниченная проба (`check`, `count`, малый `--limit`) — обычно не тяжёлая и делается свободно.

== 4. МУСОР — СРАЗУ (с честной оговоркой) ==

Выбрасывать **сразу, не дожидаясь приёмки**, можно:
* временное и пробы (урна исполнителя), `__pycache__`, `.tmp`;
* устаревшие копии и логи (то, что заведомо не актуально), legacy-дубли, старые бэкапы сверх нужного.

Нельзя трогать:
* чужие данные и чужие базы, единственные копии, рабочую базу программы;
* файлы вне папки программы (склад, чужое ПО, база другой машины);
* то, в чём не уверен — такое перечисляется в отчёте как кандидат.

Запись в отчёт обязательна: что убрано и сколько освободилось.

     Проверка «свои настройки есть?» — по соседям: у соседей `data\*_settings.json`, значит и у него должен быть.
17.5 **Паспорт обещает «не пишет», а папка лога есть** (`programs.json` `"logs": ""` при живой

     проверять `Test-Path` по факту.
17.6 **RC всегда 0 — это не «программа работает».** Планировщик и человек не могут отличить

     **0 нашли / 1 пусто / 2 неверный вызов** — и проверять через `cmd /c prog > nul & echo %errorlevel%`

     в логе проверяется на разумность** (время ≥ 0, счётчик ≥ 0) — иначе лог перестаёт быть доказательством.

== 16. ГРАБЛИ 03.10.2026, make_lst (сборка list.lst) ==

== 13. ГРАБЛИ 03.10.2026, copy (повторный аудит, вторая волна) ==
13.1 **Границы папки проверяются на ИМЕНИ файла, а не на результате.** `collect` копировал по
     `src/old -> dst/new`, и имя `..\..\..\data\tmp\x.prt` прошло все проверки («файл есть»),
     а файл создан ЗА пределом папки назначения (живая проба: `файл вне dst создан: True`).
     Правило: `dst_resolved = dst.resolve()`, и для каждого имени
     `d.resolve().is_relative_to(dst_resolved)`, иначе — отказ в отдельный список (`refused`).
     Проба-вред: имя с `..` надо подавать СПЕЦИАЛЬНО — обычный успешный прогон этот дефект не видит.
13.2 **Повторный аудит сразу после вчерашнего находит НОВЫЕ дефекты, а не «всё починено».**
     Вчерашние 8 были про внешний периметр (метка папки, занятый порт, журнал, заглушки);
     сегодняшние — про внутренний (границы путей, честность флагов CLI, мусор в урне, путь
     в паспорте окна). Вывод «программа чиста» по итогам вчерашней волны — не доказательство.
13.3 **Флаг CLI, объявленный и не прочитанный, — тихий обман.** `--quiet` был в `--help`,
     но переменная нигде не использовалась. Проверка одним `Select-String` по имени флага:
     одно вхождение (`add_argument`) = флаг мёртвый.
13.4 **Проба записывает в БОЕВЫЕ настройки.** Окно при проверке показало порт 8123 — след вчерашней
     пробы, записанный в `data\copy_settings.json`. Правило: окно проверять на ВРЕМЕННОМ файле
     настроек (`gui.SETTINGS = Path(tmp)`), боевой файл только читать; и сверять его с паспортом —
     расхождение «паспорт 8000 / файл 8123» само по себе находка.
13.5 **Окно надо поднимать в `mainloop`, а не через `root.update()`.** Вне цикла `root.after()` из
     фонового потока (насос `pump`) падает `RuntimeError: main thread is not in main loop`, и вывод
     службы в окно не доходит. Проба в этом виде врёт: «окно не показывает вывод службы».
     Правильный вид: `root.after(600, step1)` + `root.mainloop()`, шаги ведут по таймеру.
13.6 **Мусор программы живёт в `%TEMP%` и выглядит чужой папкой.** На этой машине `%TEMP%` =
     `D:\PTC\CREO-LOCAL-SETUP\TEMP`; там накопились 10 папок `creo_copy_*` за одну ночь — их не видно
     при разборе дома и некому убирать, кроме кнопки пользователя. Лечится дважды: свой каталог
     урны (`TMP_DIR`) И авто-уборка помеченных папок при старте службы.
