# ВЫЖИВАНИЕ ЛОКАЛЬНОГО ИИ В CLINE (VS Code), редакция 17.09.2026

Кому: локальным моделям (gemma4:26b, окно ~131k) и любому исполнителю в Cline.
Закон дома — `D:\AI\repo\MANIFEST.md` (читается первым); дельта среды Cline — `D:\AI\.clinerules`.
Этот файл — свод привычек, которые гасят частые вылеты (все они лежат в `D:\AI\repo\crash\`).

## 1. ПРИВЫЧКИ ПРОТИВ ВЫЛЕТОВ (главное)
1. Сообщение заканчивается ЛИБО вызовом инструмента, ЛИБО явным маркером
   «ПАУЗА: жду слова пользователя». Тихо закончить рассуждением нельзя (crash_agent_silence).
2. Пересказ плана — не шаг (13.2): план сложился → в том же сообщении идут вызовы.
   Не повторять один и тот же план 3+ раза (crash_plan-loop-replan-no-exec).
3. Мини-спека на ногу — до 5 шагов; длинную задачу дробить и передавать якорем (13.12).
4. Контекст экономить: читать только нужные файлы (1-2 за раз), большие файлы — диапазонами
   по якорям, не тащить в контекст простыни. 131k не бесконечны: держи в окне цель и якорь.
5. Больше ~20 вызовов на ногу — остановка, отчёт, передача.

## 2. ТРАНСПОРТ run_commands (PowerShell)
1. Одна команда ≤ 25 секунд: таймаут инструмента 30 с, а Start-Sleep его съедает
   (crash_command-30s-timeout). Ожидание — чанками по 20-25 с, длинное — детачем в лог.
2. Питон живёт ТОЛЬКО в .py-файле, запуск: `cmd /c "python -X utf8 file.py > out 2>&1"`,
   чтение: `Get-Content -Path out -Encoding utf8`. Инлайн `-c` через PowerShell обрезает
   stderr и врёт (crash_ctl-inline-stderr-truncated).
3. Кавычки — без обратных слэшей; сложные строки выносить в .py/.ps1
   (crash_quoted-escape-parse-failure).
4. Не читать файл в той же пачке, где его создали: после `Copy-Item` сначала `Test-Path`,
   потом чтение (crash_runcommands-copy-race).
5. Параметры командлетов — из живой цитаты (`Get-Help`/`Get-Command`), не из памяти:
   у `Get-Content` нет `-LineNumber` (есть `-TotalCount`, `-Tail`; номера строк — `Select-String`).
6. Кириллицу консоль не несёт: verbatim-русский входит в файлы только через редактор;
   ASCII-скрипты — с эскейпами \uXXXX.
7. ПРОТОКОЛ ОЖИДАНИЯ ДЕТАЧ-ПРОЦЕССА: запустил детач → ОДИН контрольный опрос
   через 20-25 с; результата нет → стоп-отчёт («запущено, PID, где будет результат,
   приёмка в следующей ноге»); второй опрос того же файла ЗАПРЕЩЁН
   (crash_sleep-poll-loop-after-timeout). Тяжёлые приёмки гонять на изолированном
   тестовом корне, не по живым сетевым дискам.

## 3. РЕДАКТОР (editor / write_file)
1. Блоки правки — до 3 КБ; `old_text` брать из СВЕЖЕГО чтения, а не по памяти.
2. «text not found» = устаревший якорь или CRLF/LF-расхождение
   (crash_editor-text-not-found, crash_editor-mismatch): укоротить якорь, перечитать файл,
   либо якорный патч ASCII-скриптом (скрипт сам проверяет, что якорь найден, и НЕ пишет
   файл, если нет).
3. Файла нет → `write_file` одним вызовом; файл есть → правка якорями.
полная замена файла = один write_file по существующему пути (перезапись, old_text не нужен, удаление не нужно); Remove-Item по файлам дома без прямого слова пользователя = нарушение пункта 5 манифеста, veto.
4. Большой файл не собирать вставками вразнобой (5.8): либо один полный вызов, либо
   дописывание строго у последней строки.
5. После правки .py — `py_compile`; после правки витрины — `dev\ui_probe.py` и `dev\ui_check.py`.
6. Приёмка UI — только в живом браузере (Ctrl+F5, чистая консоль, слово пользователя).

## 4. КРАХ: ЧТО ДЕЛАТЬ
1. Отчёт в задаче (что делал, строка ошибки дословно) + скил в `crash\` по шаблону
конституции.
2. Та же подпись повторилась — прочитать профилактику скила и увеличить счётчик;
3+ = пользователю.
3. ОТВЕТ ВОСКРЕШЕНИЯ — НЕДЕЛИМЫЙ АТОМ (одно сообщение, четыре точки в этом порядке,
пропусков нет): 1) read_file D:\AI\repo\SKILL_local_agent_cline.md целиком одним
вызовом; 2) если диагностика назвала подпись с крах-скилом в crash\ — прочитать и его;
3) диагностика: пять вопросов цитатами + якорь (что на диске + следующий шаг);
4) строка-доказательство в конце того же сообщения: «скилл выживания прочитан;
крах-скил: <имя или нет>». Сообщение без любой из четырёх точек = неполное =
нарушение; в режимах Crash/Revive оптимизация вызовов и чтений запрещена: ритуал —
механизм синхронизации, а не накладной расход (crash_omission_of_revive_protocol).
Сначала зафиксируй, потом лечи.
4. Упавший шаг дословно не повторять: либо смена метода, либо процитированная
причина (13.2/7).

ОБРАЗЕЦ ДИАГНОСТИКИ (живой пример дома, 18.09.2026, спека 76 Ф1):
1) Что делал? Фаза Ф1: полная замена MANIFEST.md текстом из ПРИЛОЖЕНИЯ А.
2) Какие инструменты и результаты? read_files — содержимое; editor — отказ
«Editor input too large» (old_text 8 КБ), затем «Invalid input: expected string,
received undefined» на повторе того же блока.
3) Что хотел получить? Полную замену содержимого файла одним движением.
4) Что не получалось? editor отверг блок выше лимита; дословный повтор блока ушёл
в клиентский отказ.
5) Почему встал? Выбран неверный инструмент: полная замена файла — это один
write_file по методу спеки, а не editor с old_text во весь файл.
Якорь: бекап pre_spec75_manifest.bak создан; MANIFEST.md существует.
Следующий шаг: ОДИН write_file полным текстом приложения (смена метода по М7 —
возврат к методу спеки); план «разбить на два editor» отменён словом пользователя
как повтор той же болезни кусочками.
Как читать образец: вопросы 1-4 — факты с цитатами, вопрос 5 — корневая причина
(не «сработал триггер»), якорь — что уже на диске, следующий шаг — смена метода,
а не повтор упавшего хода; родство подписи — crash_editor-oversize-zod-undefined.
Образец доатомный: современное сообщение воскрешения сверх показанного содержит
точку 1 (чтение этого файла) и точку 4 (строку-доказательство) — см. атом в пункте 3.

## 5. ГИГИЕНА ДАННЫХ
1. tmp — только для проб; каждый файл — в списке отчёта, потом удаление.
2. Удаления вне `data\tmp` и `data\backup` — только по прямому слову пользователя в задаче.
3. Важное из tmp сразу переносить в постоянный файл: «сохрани или потеряешь»
   (crash_missing-temp-artifacts).
4. Не трогать чужие артефакты в tmp и чужие процессы (дубли сервисов, сторожей) без слова.
5. Секреты и токены в цитатах — голова 4 символа; вход — учётка из `data\secrets.json`, одна попытка.
\nОТЧЁТЫ И ЛОГИ — ОДНА ПАПКА D:\AI\log: финальный отчёт ноги = файл D:\AI\log\reports\REPORT_<спека|задача>_<исполнитель>_<дата>.md, пишется ДО последней строки чата без напоминания; последняя строка чата содержит указатель отчёта. Временные файлы ИИ (писатели, патчи, out.txt) — только в свою урну D:\AI\log\urn\<исполнитель>\, в tools\data\tmp больше не пишутся. Программы агента пишут логи каждая в свою подпапку D:\AI\log\<имя программы>\. Автоуборка log_clean.py по retention.json, вне D:\AI\log не трогает ничего. Память дома (SPEC, PROGRESS, crash, манифест) живёт в репо под гитом и не чистится.

## 7. ЧЕК-ЛИСТ ПЕРЕД КАЖДЫМ ХОДОМ
1. Какой это шаг спеки и что я жду получить? 2. Каким инструментом? 3. Мой old_text свежий?
4. Команда уложится в 25 с? 5. Нет ли в цитате секрета? 6. Чем докажу результат (проба/компиляция)?
7. Если что-то упало — успел ли я зафиксировать частичное состояние?
8. Шаг дольше 60 с? Оценил ли длительность ДО запуска? Есть ли план Б?
9. Это уже 2-я попытка того же хода? Если да — смена метода или отчёт (М7).
10. После рестарта — трёхчастная приёмка: netstat «один LISTENING на 8765», agent.pid равен живому PID, StartTime больше mtime правленых файлов (crash_agent-duplicate-restart-race).
