# ВЫЖИВАНИЕ ЛОКАЛЬНОГО ИИ В CLINE (VS Code)

**Кому:** локальным моделям (`gemma4:26b`, `gpt-oss:20b`, `qwen3.6-35b` и др.) при работе в Cline.
**Главный закон среды:** `D:\AI\.clinerules` (подставляется в системный промпт автоматически).
*(Примечание: `D:\AI\repo\MANIFEST.md` — расширенный закон для автономного Python-агента, для Cline-задач читать его не требуется).*

## 1. ПРИВЫЧКИ ПРОТИВ ВЫЛЕТОВ И ПЕТЕЛЬ

1. **Завершение хода:** сообщение заканчивается либо вызовом инструмента, либо явным маркером «ПАУЗА: жду слова пользователя». Тихо закончить рассуждением без действия нельзя (`crash_agent_silence`).
2. **План — не шаг:** если план готов — сразу вызывай инструмент. Не повторяй один и тот же план 3 раза подряд без исполнения (`crash_plan-loop-replan-no-exec`).
3. **Экономия контекста:** читай только нужные файлы (1–2 за раз). Большие файлы читай диапазонами строк по якорям, не загружай весь файл целиком без необходимости.

**Необязательный приём для гигантских выводов (> 100 строк):** если скрипт или поиск выдаёт огромную таблицу, которую консоль обрезает или которая забьёт окно, можно (по усмотрению, не обязательно) сбросить её во временный файл `D:\AI\log\urn\cline\scan_<тема>.json`, прочитать нужную сводку и сразу удалить файл. Для обычных ответов субагент возвращает сжатый текст напрямую без файлов.
4. **Контроль усталости ноги:** следи за количеством вызовов инструментов по правилам `D:\AI\repo\SKILL_noga_health.md` (пороги внимания: 40, 55, 70 вызовов; при двух признаках деградации — передача эстафеты).
5. **Сенсор петель (онлайн):** петля = повтор **того же** `инструмент+аргументы` (особенно после ошибки); перед вызовом сверь с последними 2 шагами. **НЕ петля:** чтение разных файлов подряд одним `read_files`, серия разных команд (аргументы разные). После ошибки и каждые ~6 вызовов — само-аудит (`CLINE\SKILL_cline_session_audit.md`); ≥2 совпадения одного вызова — REVIVE и смена метода.
6. **Бумаги сразу, по ходу (защита от смерти окна):** открытия, разбор, интересное — записывай **мелкими шагами сразу**, а не в конце ноги; в записи давай **ТОЧНОЕ указание скилла и параграфа** (`SKILL_…md §N`), чтобы при крахе или эстафете не искать заново. Отчёт всё равно пишется — но по готовым заметкам, а не по памяти. Причина: `crash\SKILL_crash_cline_longsession_context_death.md` (ПОВТОРЫ 6) — длинная нога молча обрывается, и незаписанное знание теряется.
7. **Петля — факт вызовов, не слово в тексте (находка 26.11.2026):** детектор `plan-loop` сторожа считал петлёй текст, где есть слово «план» и нет слова «вызов» (лексический предикат). **Ложные срабатывания** на нормальной работе («план: прочту, потом правлю» + реальное исполнение), **пропуски** («план: сделаю вызов editor» без исполнения). Правильный предикат — **поведенческий: между повторяющимися планами НЕ было вызовов инструментов**. Для ноги-исполнителя: если 3+ хода идут обсуждение/планы без правок и команд — это **реальная петля**, даже если тексты разные. См. `crash\SKILL_crash_plan-loop-replan-no-exec.md`.
8. **`ГРАБЛИ.md` — журнал стенда, ищи здесь (находка 26.11.2026):** журнал ошибок **стенда** (не дома) лежит `D:\AI\AGENT_SETTINGS\ГРАБЛИ\ГРАБЛИ.md`; общие грабли дома — `D:\AI\repo\SKILL_grabli_general.md`. Ошибаешься (не тот инструмент, не та формулировка, ошибка стенда) → сначала **прочти ГРАБЛИ.md**, потом делай. В `crash\` — только инфраструктурные сбои, в `ГРАБЛИ.md` — логические ошибки.

## 2. РЕЖИМЫ РАБОТЫ И МИКРО-СУБАГЕНТЫ (v3.0)

**Две НЕЗАВИСИМЫЕ оси (комбинируются!):** темп (`§2.1 ПОШАГОВО` | `§2.2 АВТОНОМНО`) × исполнитель (главное окно | `§2.3 ДИСПЕТЧЕР`). Пример: `ДИСПЕТЧЕР ПОШАГОВО` — работу делают субагенты, а главное окно останавливается на подтверждении после каждого шага; `ДИСПЕТЧЕР АВТОНОМНО` — субагенты идут до конца. Голое `ДИСПЕТЧЕР` может остановиться для уточнения; жёсткая автономия — только по слову `АВТОНОМНО`. **Смена режима посреди задачи** — новой командой владельца, со следующего шага.

### §2.1 ПОШАГОВО (ПОШАГОВО, ПО ШАГАМ, ШАГ ЗА ШАГОМ, ПОЭТАПНО, ПО ЭТАПАМ, ПО ОДНОМУ ШАГУ, С ОСТАНОВКАМИ, С ПОДТВЕРЖДЕНИЕМ)
Логика: 1 действие -> краткий отчёт -> пауза до подтверждения хода пользователем.

### §2.2 АВТОНОМНО (АВТОНОМНО, ДО КОНЦА, ДОДЕЛЫВАЙ ВСЁ, ДЕЛАЙ ПОЛНОСТЬЮ, ПОД КЛЮЧ, БЕЗ ОСТАНОВОК, БЕЗ ВОПРОСОВ, САМ БЕЗ ВОПРОСОВ)
Логика: непрерывный цикл без промежуточных вопросов; **уточнения копятся и выдаются разом в конце работы** (АВТОНОМНО остановку на вопросы НЕ приветствует). **Исключение:** если без уточнения следующий шаг невозможен — заверши ход кратким отчётом-уточнением (это не петля). Авто-торможение (**Downshift**) при заполнении окна `>= 70%` (от рабочего `num_ctx`, см. `.clinerules` §1.7) или при 1-м сжатии — снижение темпа и подготовка эстафеты `ESTAFETA_<ТЕМА>.md`.

### §2.3 ДИСПЕТЧЕР (ДИСПЕТЧЕР, СУБАГЕНТАМИ, ЧЕРЕЗ СУБАГЕНТОВ, МАКСИМУМ СУБАГЕНТОВ, БЕРЕГИ ОКНО, ЭКОНОМНО, ЭКОНОМЬ КОНТЕКСТ, ДЕЛЕГИРУЙ) и автоопределение среды
**`ДИСПЕТЧЕР` может остановиться для уточнения информации**, если данных не хватает (в отличие от `АВТОНОМНО`).
**Ветка А (`spawn_agent` доступен) — регламент 4 ролей:**
- **Библиотекарь** — поиск в `D:\AI\repo\SKILL_index.md` и индексах веток; возвращает точные пути и диапазон строк для чтения.
- **Разведчик** — анализ кода/файлов и сбор фактов с диска.
- **Арбитр** — включается при промахе Библиотекаря или сомнительном ответе Разведчика; перепроверяет вывод независимо.
- **Тестировщик** — запуск и проверка результата (команды, тесты, `git diff`).
- Формат ответа субагента: `SUMMARY <= 12 строк`.
- **Зачем субагент (теория):** он защищает окно ГЛАВНОЙ модели — рутинное чтение и сканы делает субагент, чтобы основная нога не съедала своё окно. Давай субагенту узкий диапазон `20–40` строк и точные пути. Отчёт субагента не отменяет личного чтения скиллов перед правкой. **Окно субагента — полное (как у модели), не урезанное** — экономится только окно главной ноги. Субагент НЕ печатает ни футер `[НОГА: …]`, ни маяк `[START: …]` (правило §0 на субагентов не действует).
- **Схема субагентов бывает разной:** `spawn_agent` (одна) и `team_spawn_teammate` + `team_run_task` (другая, «teams»). Сначала проверь, какие инструменты реально доступны и их схему; ключи наугад не подставляй. Если `team_run_task` вернул «teammate not found» — teammate не создан: исправь создание, **НЕ повторяй тот же вызов** (`.clinerules` §4.7).

**Ветка Б (`spawn_agent` недоступен — VS Code Cline / внутри субагента) — Solo-Chunked:**
- Главное окно само ищет через `Select-String` и читает `<= 80` строк за раз.
- Ранний порог сдачи эстафеты — при заполнении `55–60%` окна.

### §2.4 КОМАНДЫ-АРТЕФАКТЫ (ПЛАН / ЭСТАФЕТА / ПРОМПТ) — это НЕ режимы
- **ПЛАН** (`ПЛАН`, `СДЕЛАЙ ПЛАН`) → `D:\AI\ЭСТАФЕТЫ\PLAN_<ТЕМА>.md` (дорожная карта). Регламент — `SKILL_handover.md` §2.
- **ЭСТАФЕТА** (`ЭСТАФЕТА`, `ДЕЛАЙ ЭСТАФЕТУ`, `ДАЙ ЭСТАФЕТУ`, `ПЕРЕДАЙ НОГУ`, `ПЕРЕДАЙ СЛЕДУЮЩЕЙ НОГЕ`, `СДАЙ СМЕНУ`, `HANDOVER`) → `ESTAFETA_<ТЕМА>.md` — слепок состояния для продолжения ТОЙ ЖЕ работы (в т.ч. при нормальной сдаче смены). Регламент — `SKILL_handover.md` §3.
- **ПРОМПТ** (`СОСТАВЬ ПРОМПТ`, `НАПИШИ ПРОМПТ`, `ДАЙ ПРОМПТ`, `ПРОМПТ НА НОВОЕ ОКНО`, `ПРОМПТ ДЛЯ НОВОЙ НОГИ`) → самодостаточный стартовый промпт для новой ноги (ТЗ на НОВУЮ работу после разведки). Голое слово `ПРОМПТ` — НЕ триггер. Регламент — `SKILL_start_prompt.md`.

## 3. ТРАНСПОРТ И РЕДАКТОР (Ссылки на правила)

## 4. КРАХ И ВОСКРЕШЕНИЕ (Протокол REVIVE)

Если пользователь пишет слова-триггеры (**КРАХ, ВСТАЛ, ПЕТЛЯ, ВЫЛЕТЕЛ**, а также вылет, цикл, завис, опять то же, продолжай после Cancel), модель сама открывает режим восстановления.

### Порядок ответа при REVIVE:
1. **Первая строка ответа:** строго маркер `REVIVE:` (машиночитаемый тег).
2. **Диагностика по контексту (5 вопросов кратко):**
   - Что делал (шаг, файл, команда)?
   - Какие инструменты вызывал и что получил?
   - Какой результат хотел получить?
   - Что пошло не так (точная строка ошибки или симптом)?
   - В чем причина сбоя (гипотеза)?
3. **Якорь и следующий шаг:** зафиксируй, что уже есть на диске, и предложи **смену метода** (повторять упавший ход дословно запрещено).
4. **Фиксация в базе крахов:** сверь подпись ошибки с `D:\AI\repo\crash\SKILL_crash_index.md`. Если подпись известна — прочитай профилактику и увеличь счетчик `ПОВТОРЫ` в ее файле; если ошибка новая — оформи скилл по шаблону из `D:\AI\repo\crash\SKILL_crash_constitution.md`.

## 7. ЧЕК-ЛИСТ ПЕРЕД ВАЖНЫМ ДЕЙСТВИЕМ

1. **Якорь свежий?** Беру ли я `old_text` из свежего чтения файла, а не по памяти или из вывода консоли?
2. **Размер в лимите?** Укладывается ли блок правки в 5 КБ?
3. **Команда быстрая?** Уложится ли вызов консоли в 25 секунд и нет ли в нем инлайн-кириллицы?
4. **Безопасность:** Не затрагивает ли команда сетевой диск `Z:` на запись или чужие процессы по общему имени?
5. **Это не повтор?** Если этот метод уже упал дважды подряд — я меняю метод, а не повторяю попытку.
6. **После рестарта сервиса:** проверил ли я порт (`LISTENING`), совпадение `PID` и время запуска процесса?

## 8. ЗАМЕР ЗАПОЛНЕНИЯ ОКНА КОНТЕКСТА (без скриптов)

Cline хранит историю и токены **по каждой сессии**. Заполнение окна (термин: окно = `contextWindow` у облачных моделей / `num_ctx` у Ollama) = `inputTokens` последнего ответа ассистента.

**Файлы (Cline standalone):**
* История сессии: `%USERPROFILE%\.cline\data\sessions\<session_id>\<session_id>.messages.json`
* Окно MAX: `%USERPROFILE%\.cline\data\globalState.json` → `actModeOpenAiModelInfo.contextWindow` (или `ollamaApiOptionsCtxNum`, если `actModeApiProvider = ollama`).
* (Для VS Code-расширения база — `%APPDATA%\Code\User\globalStorage\saoudrizwan.claude-dev\`.)

**Прямой запрос (одна команда, файл-скрипт не нужен):**
```powershell
$s = Get-ChildItem "$env:USERPROFILE\.cline\data\sessions" -Directory | Sort LastWriteTime | Select -Last 1
$d = Get-Content "$($s.FullName)\$($s.Name).messages.json" -Raw | ConvertFrom-Json
@($d.messages | ? { $_.role -eq 'assistant' -and $_.metrics.inputTokens })[-1].metrics
```

**Формула:** заполнение = `inputTokens` последнего ответа; `% = inputTokens / contextWindow`; стоп-порог = MAX × 0.70.
**🔴 Знаменатель ≠ база:** для `provider=ollama` окно = **контекст модели** (`/api/ps` → `context_length`, напр. `262144`); для облачных — `contextWindow`; `DEFAULT_MAX_CTX = 131072` — только крайний fallback, НЕ подставлять вместо реального окна.

**Правила:**
* **Не** брать заполнение из `session.json → usage` — это КУМУЛЯТИВНАЯ сумма inputTokens по всем запросам, а не текущее окно (вдобавок она отстает).
* Скрипт-файл не обязателен: запуск скрипта и прямой запрос — равнозначные инструментальные вызовы. Для отладки («перестало отдавать нужное») **предпочтителен прямой запрос**.
* Ollama `/api/ps` брать только если провайдер = ollama: его реестр не видит облачных/туннельных провайдеров.
* Файл сессии обновляется каждый ход — перечитывать перед утверждением (свежесть).
