# ВЫЖИВАНИЕ ЛОКАЛЬНОГО ИИ В CLINE (VS Code), редакция 21.09.2026
Закон трёх рук из манифеста — инструмент строится сразу тремя руками, а не добирается позже.

Кому: локальным моделям (gemma4:26b, окно ~131k) и любому исполнителю в Cline.
Закон дома — `D:\AI\repo\MANIFEST.md` (читается первым); дельта среды Cline — `D:\AI\.clinerules`.
Этот файл — свод привычек, которые гасят частые вылеты (все они лежат в `D:\AI\repo\crash\`).

## 1. ПРИВЫЧКИ ПРОТИВ ВЫЛЕТОВ (главное)
1. Сообщение заканчивается ЛИБО вызовом инструмента, ЛИБО явным маркером
   «ПАУЗА: жду слова пользователя». Тихо закончить рассуждением нельзя (crash_agent_silence).
2. Пересказ плана — не шаг (13.2): план сложился → в том же сообщении идут вызовы.
   Не повторять один и тот же план 3+ раза (crash_plan-loop-replan-no-exec).
3. Мини-спека на ногу — до 5 шагов; длинную задачу дробить и передавать якорем (13.12).
4. Контекст экономить: читать только нужные файлы (1-2 за раз), большие файлы — диапазонами
   по якорям, не тащить в контекст простыни. 131k не бесконечны: держи в окне цель и якорь.
5. Больше ~20 вызовов на ногу — остановка, отчёт, передача.

## 2. ТРАНСПОРТ run_commands (PowerShell) — СМ. `SKILL_edit_gotchas.md` §26

Все грабли транспорта (таймауты 30 с, Start-Sleep, инлайн `python -c`, кавычки, `Test-Path`
после `Copy-Item`, параметры командлетов, кириллица консоли, протокол детаж-процесса) вынесены
в `D:\AI\repo\SKILL_edit_gotchas.md` §26. Читать ПЕРЕД любым вызовом `run_commands`.

## 3. РЕДАКТОР (editor / write_file) — СМ. `SKILL_edit_gotchas.md` §0–§1

Все грабли редактора вынесены в `D:\AI\repo\SKILL_edit_gotchas.md` §0–§1. Читать ПЕРЕД любой правкой `editor`/`write_file`.

## 4. КРАХ: ЧТО ДЕЛАТЬ
Сообщение пользователя о тихой смерти или вставка консоли/скрина = достаточная цитата краха; новая нога пишет крах-скилл от имени умершей с пометкой источника цитаты.
Отчёт в задаче (что делал, строка ошибки дословно) + скил в `crash\` по шаблону
конституции.
Та же подпись повторилась — прочитать профилактику скила и увеличить счётчик;
3+ = пользователю.
Сначала зафиксируй, потом лечи.
Упавший шаг дословно не повторять: либо смена метода, либо процитированная
причина (13.2/7).
ОТВЕТ ВОСКРЕШЕНИЯ — НЕДЕЛИМЫЙ АТОМ (одно сообщение, пять точек в этом порядке,
пропусков нет): 1) read_file D:\AI\repo\SKILL_local_agent_cline.md целиком одним
вызовом; 2) если диагностика назвала подпись с крах-скиллом в crash\ — прочитать и его,
профилактика до хода, а не после; 3) диагностика: пять вопросов цитатами + якорь
(что на диске + следующий шаг); 4) РЕГИСТРАЦИЯ: подпись с живым скиллом = счётчик +1
в нём с цитатой строки; подпись новая = write_file нового скилла в crash\ по шаблону
конституции в том же сообщении; не можешь писать скилл сейчас = строка в сообщении
«скилл долг: <подпись>, причина, запишу следующим шагом»; без вызова регистрации или
долговой строки атом неполон = нарушение; лечебные вызовы (editor, правки, лечение)
в сообщении ДО регистрации запрещены; 5) строка-доказательство в конце того же
сообщения: «скилл выживания прочитан; крах-скил: <имя | создан <имя> | долг>» —
без токена регистрации строка неполна, и нарушение видно с одного взгляда пользователя.
Сообщение без любой из пяти точек = неполное = нарушение; в режимах Crash/Revive
оптимизация вызовов и чтений запрещена: ритуал — механизм синхронизации, а не
накладной расход (crash_omission_of_revive_protocol).

ОБРАЗЕЦ ДИАГНОСТИКИ (живой пример дома, 18.09.2026, спека 76 Ф1):
1) Что делал? Фаза Ф1: полная замена MANIFEST.md текстом из ПРИЛОЖЕНИЯ А.
2) Какие инструменты и результаты? read_files — содержимое; editor — отказ
«Editor input too large» (old_text 8 КБ), затем «Invalid input: expected string,
received undefined» на повторе того же блока.
3) Что хотел получить? Полную замену содержимого файла одним движением.
4) Что не получалось? editor отверг блок выше лимита; дословный повтор блока ушёл
в клиентский отказ.
5) Почему встал? Выбран неверный инструмент: полная замена файла — это один
write_file по методу спеки, а не editor с old_text во весь файл.
Якорь: бекап pre_spec75_manifest.bak создан; MANIFEST.md существует.
Следующий шаг: ОДИН write_file полным текстом приложения (смена метода по М7 —
возврат к методу спеки); план «разбить на два editor» отменён словом пользователя
как повтор той же болезни кусочками.
Как читать образец: вопросы 1-4 — факты с цитатами, вопрос 5 — корневая причина
(не «сработал триггер»), якорь — что уже на диске, следующий шаг — смена метода,
а не повтор упавшего хода; родство подписи — crash_editor-oversize-zod-undefined.
Образец доатомный: современное сообщение воскрешения сверх показанного содержит
точку 1 (чтение этого файла) и точку 5 (строку-доказательство) — см. атом в пункте 4
этого файла.

## 5. ГИГИЕНА ДАННЫХ
1. tmp — только для проб; каждый файл — в списке отчёта, потом удаление.
2. Удаления вне `data\tmp` и `data\backup` — только по прямому слову пользователя в задаче.
3. Важное из tmp сразу переносить в постоянный файл: «сохрани или потеряешь»
   (crash_missing-temp-artifacts).
4. Не трогать чужие артефакты в tmp и чужие процессы (дубли сервисов, сторожей) без слова.
5. Секреты и токены в цитатах — голова 4 символа; вход — учётка из `data\secrets.json`, одна попытка.
ОТЧЁТЫ И ЛОГИ — ОДНА ПАПКА D:\AI\log: финальный отчёт ноги = файл D:\AI\log\reports\REPORT_<спека|задача>_<исполнитель>_<дата>.md, пишется ДО последней строки чата без напоминания; последняя строка чата содержит указатель отчёта. Временные файлы ИИ (писатели, патчи, out.txt) — только в свою урну D:\AI\log\urn\<исполнитель>\, в tools\data\tmp больше не пишутся. Программы агента пишут логи каждая в свою подпапку D:\AI\log\<имя программы>. Автоуборка log_clean.py по retention.json, вне D:\AI\log не трогает ничего. Память дома (SPEC, PROGRESS, crash, манифест) живёт в репо под гитом и не чистится.

## 7. ЧЕК-ЛИСТ ПЕРЕД КАЖДЫМ ХОДОМ
1. Какой это шаг спеки и что я жду получить? 2. Каким инструментом? 3. Мой old_text свежий?
4. Команда уложится в 25 с? 5. Нет ли в цитате секрета? 6. Чем докажу результат (проба/компиляция)?
7. Если что-то упало — успел ли я зафиксировать частичное состояние?
8. Шаг дольше 60 с? Оценил ли длительность ДО запуска? Есть ли план Б?
9. Это уже 2-я попытка того же хода? Если да — смена метода или отчёт (М7).
10. После рестарта — трёхчастная приёмка: netstat «один LISTENING на 8765», agent.pid равен живому PID, StartTime больше mtime правленых файлов (crash_agent-duplicate-restart-race).
11. После обморока/вылета окна Cline первым делом — свежие строки `hooks.jsonl`, ЕСЛИ лог ведётся
    (`Get-ChildItem 'D:\AI\log' -Filter 'hooks.jsonl'`): причина смерти читается до диагностики,
    не по памяти. **Лога нет — честно писать «причина вылета неизвестна: hooks.jsonl не
    ведётся», цитату не выдумывать** (crash_cline_longsession_context_death, ПОВТОРЫ: 3).

## 9. АНТИ-ПЕТЛЯ И ДЕТСКИЕ ОШИБКИ
Полный свод правил — в `.clinerules` §5.1–5.2; подписи крахов — файлы в `crash\`
(каждая строка оплачена потерянной сессией). Ключевое: два одинаковых вызова = смена метода
(третий = петля); инлайн `python -c` запрещён; детач — ОДИН опрос через 20–25 с; шаг > 60 с
без плана Б не запускать; пересказ плана — не шаг. `editor` > 6 КБ, `insert_line` по номерам,
правка без `old_text` — запрещены; `old_text` только из свежего `read_files`; не читать файл
в пачке, где его создали (сначала `Test-Path`); удаления вне `data\tmp`/`data\backup` — по слову.
**В петле:** СТОП → назвать подпись вслух («это crash_…: повтор того же хода») → сменить метод
ИЛИ стоп-отчёт с якорем → счётчик в крах-скиле (3+ одной подписи → пользователю).
