ОШИБКА (дословно, для grep):
Editor input too large: new_text was ... characters, exceeding the recommended limit of 6000.
СИМПТОМ: цикл неудачных вызовов editor или ошибка о нескольких совпадениях.
ПРИЧИНА: попытка переписать файл целиком через editor либо неуникальный old_text в файле с дублями.
ПРОФИЛАКТИКА:
1. Большие файлы — дробить правку на несколько вызовов мелкими кусками old_text/new_text.
2. Неуникальный текст — искать уникальные якоря (окружающие строки) или перезаписывать через run_commands.
3. Сильно повреждённый файл (дубли) — восстановить из последнего чистого коммита git и писать домовым каналом (один write_file до 8 КБ либо часть 1 + дописывание строго у последней строки); PowerShell Set-Content для файлов с кириллицей запрещён — консоль её не поддерживает.
4. **ПОВТОР 2 (02.10.2026, дважды за сутки): `old_text` = целый заголовок `## N.` съедает его сам.** Обе правки выглядели как «вставка блока перед разделом», а на деле удаляли заголовок: содержимое раздела оставалось «сиротой» в конце файла. Правило, записанное в отчёт 02.10 после первого случая, **не сработало на второй день**. Профилактика:
   - **никогда не делать `old_text` равным заголовку**; якорь — 2-3 строки ниже заголовка;
   - **после каждой правки файла с разделами — один `Select-String '^## '`** и сверка числа
     разделов до/после. Правило §9.2 п.8 витрины («цитата числа вхождений ДО и ПОСЛЕ») —
     работает не только для витрины, а для любого файла со структурой;
   - отсутствие заголовка в выводе проверки — не мелочь, а признак того, что блок «уехал».
5. **Способ проверки дешёвый:** `(Select-String -Path F -Pattern '^## ' | Measure-Object).Count`
   ДО и ПОСЛЕ правки. Разница ≠ 0 при добавлении блока = структура поехала.
