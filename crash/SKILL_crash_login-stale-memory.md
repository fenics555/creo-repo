СЧЁТЧИК ПОВТОРОВ: 2
ОШИБКА (дословно, для grep):
{"error": "нужен вход"} — POST /login при верном пароле; проверка users.check_login
падала на расхождении источников
СИМПТОМ: любой логин в агента отвергается. data\secrets.json содержит один пароль,
data\users.json на диске — хэш другого (кто-то из исполнителей перезаписал), а бегущий
процесс агента держит в памяти устаревший блок users со старта. Плюс возможный лок-аут
после перебора учёток.
ПРИЧИНА: три источника правды о пароле разошлись и не перечитываются вместе: файл
секретов, файл пользователей и память процесса.
ЛЕЧЕНИЕ (проверено 17.09.2026, цитаты в транскрипте):
1. Сбросить пароль из secrets.json при бегущем агенте:
   python -X utf8 -c "import json,users; pw=json.load(open('data/secrets.json',encoding='utf-8'))['admin_pw']; print(users.admin_reset_password('admin', pw))"
   Живой вывод: LOGINS: ['admin', '555', 'testadmin']; RESET ok: True; лог "admin password reset: admin".
   Список логинов пуст или ошибка — вернуть data\backup\pre_loginfix_users.json.bak в data\users.json и повторить.
2. Рестарт агента (память перечитает users.json, лок-аут обнулится). CREOSON и Ollama не трогать.
3. Проверка: POST /login {"login":"admin","pw":<секрет>} → ok=True + token; GET /status без токена → 200.
ПРОФИЛАКТИКА:
1. после любой смены пароля рестарт агента обязателен: диск и память процесса обязаны
   перечитаться вместе; без рестарта пароль живёт одновременно в двух мирах и не работает
   ни в одном.
2. учётка для входа — только из data\secrets.json (ключ admin_pw), одной попыткой;
   вход не удался дважды — СТОП и отчёт, третьей попытки не существует (контракт 3.5).
3. при «нужен вход» не перебирать пароли: сверить логины (users.list_users) и сбросить
   пароль из secrets.json.
   
ПРИЧИНА Б (дополнение, 17.09.2026):
Существует второй сценарий отказа входа — не расхождение трёх источников, а логин-призрак
или устаревший пароль при согласованных данных:
- secrets.json содержит полную пару admin_login + admin_pw, но users.json на диске
  не содержит пользователя admin (или содержит другого), а бегущий процесс агента
  проверяет credentials.users.check_login по своему users-блоку.
- В этом случае secrets верен, users.json неверен (или наоборот), и вход падает
  без трёх источников — только два.
РАСПОЗНАВАНИЕ:
- Если POST /login возвращает {error: "нужен вход"} при верном пароле из secrets —
  сверять список пользователей (users.list_users) ДО первой попытки входа; если admin
  нет в списке — это причина Б, а не причина А (три источника).
ЛЕЧЕНИЕ Б:
1. Либо правка secrets.json (смена admin_login/admin_pw на существующего пользователя),
   либо создание пользователя через users.add_user, либо восстановление data\backup\
   pre_loginfix_users.json.bak в data\users.json — выбор по списку пользователей.
2. После правки users.json рестарт агента обязателен (память перечитает users.json).
3. Проверка: POST /login {"login":<login>,"pw":<pw>} → ok=True + token.
ПРОФИЛАКТИКА 4-6 (дополнение):
4. Перед первой попыткой входа сверять users.list_users с contents data\secrets.json:
   если login из secrets отсутствует в users.json — это причина Б, а не А; действовать
   по Б, не по А.
5. secrets.json держит полную пару admin_login + admin_pw; users.json может быть
   расшёрст (призрак) — не смешивать источники: один пароль = один пользователь,
   проверять оба источника дискретно.
6. Призрак = правка secrets или создание пользователя, а не ретраи входа: ретраи не
   чинят расхождение, они только подтверждают его. Одна правка + рестарт — достаточно.
