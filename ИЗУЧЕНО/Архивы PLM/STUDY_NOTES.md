## 1. КАК УСТРОЕН ЧИТАТЕЛЬ (выжимка изучения, 03.10.2026)

- `creo_read.py` — единый «лобовой» парсер: `parse_toc` (секции по `#UGC_TOC`),
  `real` (double big-endian по метке `e0 02 <имя> 00 ed`), `params` (NeuPrtSld + весь файл),
  `param/compose` (шаблоны `{ИМЯ}` `"текст"` `+`), `role`, `names` (входимость),
  `user_time`/`last_hist` (история: `f7 14 <user> 00 e2 <6 байт>` и `e1 f6 e1 <user> 00 e2 <6 байт>`,

- `engine.py` — движок: `collect_stat` (обход + size/mtime), `scan_item` (паспорт одного файла),
  `do_scan` (запись в базу), `scan_to_base` (замок → черновик в %TEMP% → публикация новой
  versioned-базы `plm_reader_ГГГГММДД_ЧЧММСС.db` + бэкап + зеркала).
- `plm_reader.py` — окно + два важных для нас разборара: `history()` (ревизия/дата/пользователь/
  компьютер/версия Creo) и `parse_changes()` (**что менялось**: размеры `dNNN` из
  `MTTyped_ModifyData`, параметры из `chg_param_arr`/`param_typed_data`), `changes_line()`.
- База PLM: `snapshots` (ключ — **путь** файла), `links`, `derived`, `changes`, `folders`, `meta`.

## 2. ГЛАВНАЯ НАХОДКА: ПОЧЕМУ АРХИВЫ НЕЛЬЗЯ ЛИТЬ В БОЕВУЮ БАЗУ

`engine.do_scan` при записи:

```sql

DELETE FROM derived WHERE child=? AND source='plm_tree'
```

Ключ `snapshots` — путь, но `links`/`derived` — по модели. Старый архивный срез, пройдя
движок, **перезаписал бы связи живой базы** своими (архивными) данными: изделие, которого

Значит архивы читаем ТОЛЬКО на чтение (`engine.scan_item`) и пишем в **отдельную** базу.

## 5. СВЕРКА ОДНОИМЁННЫХ ФАЙЛОВ (главное требование хозяина: «что изменилось на что, кто и когда»)

Отдельный модуль `arch_diff.py` (та же папка). Он строит `{ключ файла: {срез: паспорт}}` и
сравнивает **соседние срезы в хронологии**: архивная дата → следующая архивная дата →
`БОЕВАЯ(сейчас)` (текущая боевая база PLM).

- **Ключ файла**: `папка\имя.прт.N` в верхнем регистре; корни `PTC\`, `D:\ARC_WORK\<дата>\`,
  `Z:\PTC\` срезаются, регистр не важен. Даты сортируются РАЗБОРОМ `дд.мм.гггг`,
  а не именем папки (иначе «02.02.2023» встало бы раньше «29.03.2022»).
- **Что сравнивается**: размер файла, объём, материал, наименование, обозначение, ревизия,
  автор, дата правки, роль, число записей истории, версия Creo, заготовка/наследование.
  Отдельно отмечаются `добавлен файл` и `файл исчез`.
- **Кто и когда**: в строку различия пишется БОЛЬШАЯ сторона — её `author` (кто правил)
  и `revdate` (когда по внутренней истории Creo) + даты файла с обеих сторон.
- Таблица `arch_diffs`: `from_date, to_date, kind, model, path_key, field, old_val, new_val,
  who, ts_hist, ts_file_old, ts_file_new, size_old, size_new`. Отчёт: `--report`.

### ГРАБЛЯ ( costing дорого, найдена на первой же сверке)

Окно PLM пишет боевую базу по правилам параметров **из `settings\settings.json`**
(`pdes/pname/pmat`), а `engine.scan_item` без `param_cfg` берёт свои умолчания
(`_PARAM_DES/_PARAM_NAME/_PARAM_MAT`). Если читать архив по умолчаниям, а сравнивать с боевой
базой — дифф полон МУСОРА: «материал `STAHL` → пусто», «наименование `X` → пусто» там, где
правок не было. Лечится одним: `scan_item(..., **load_param_cfg())`, где `load_param_cfg()`
читает `settings\settings.json`. То же касается поля `base` (заготовка): в боевой базе его нет
(есть отдельная таблица `derived`) — при сравнении с `БОЕВАЯ` это поле пропускается.

Первые цифры сверки (срез 29.03.2022 → боевой): 2 121 реальное изменение по одноимённым
файлам; добавилcя 44 249 новых файлов. Кто менял: USER 31 144, ADMIN 5 736, FENICS 135,

## 7. КАРТА / ДЕРЕВО ПРОИЗВОДСТВА: что PLM Reader собирает сам (изучено 03.10.2026)

| Что | Где в коде PLM Reader | Откуда берётся в файле Creo |
|---|---|---|
| **состав сборки** (сборка → деталь, количество) | `links(parent, child, qty, source='plm_tree')`, заполняется в `do_scan` | `creo_read.names()` — имена `*.prt/.asm/*.drw`, встречающиеся внутри файла; счётчик вхождений = количество |
| **заготовка / отливка / отражение** | `derived(child, base, kind, source='plm_tree')` + роль `nasled.X` (наследование) и `proizv.X` (производная) | `MERGE_BASE_PART` → «наследование» (в т.ч. отражение); `ref_part_tab` → «производная», имя сверяется с моделями той же папки |
| **модельная оснастка** | роль `MFG` в `snapshots` + `mfg_models()` (по связи и по префиксу имени) | признак `ASSEM_MFG` в первых 400 байтах файла |
| **верхние сборки** | вычисляется на лету: `links`, где `parent` не встречается как `child` | — |
| **объём** | `snapshots.volume` | `e0 02 volume 00 ed <double BE>` |
| **материал / обозначение / наименование** | `snapshots.material/designation/name` | параметры по правилам из `settings\settings.json`, читаются по всему файлу в UTF-8 и cp1251 |
| **журнал изменений** | `changes` | разница паспортов между сканами **плюс** `parse_changes` (имена размеров `dNNN`, параметры) по ревизиям |
| **обратная связь «заготовка → потомки»** | `derived_children()` по индексу `ix_derived_base` | — |

**ЧЕГО PLM Reader НЕ СОБИРАЕТ:** инструменты мануфактуринг-сборок. В MFG-файле (`ASSEM_MFG`)
есть `tool_table` (4 вхождения), `TOOL_ID` (3), номера `T0001` и операции `OPERATION`/`NC_SEQ` —
проверено пробой на `Z:\PTC\Work\00080\00080-03.asm.1`. В боевой базе только признак роли `MFG`,
самих инструментов нет. Поэтому `archive_scan.py` читает их сам (`read_tools`) в `arch_tools`.

### Как это дописывается в БОЕВУЮ базу (требование хозяина: «дописать в начало, что было ДО»)

Модуль `arch_merge.py`. Ключевое решение — **не трогать** `snapshots/links/derived`:

- `snapshots.path` — первичный ключ по пути; архивный файл того же изделия имеет другой путь,
  и дописывание архивных путей сломало бы инкрементальный скан (окно сочло бы их «пропавшими»);
- `links`/`derived` скан чистит по `source='plm_tree'` — архивные связи с другим `source`
  пережили бы скан, но окно их не показывает.

Поэтому история «до» живёт в **отдельных таблицах `arch_*` В ТОЙ ЖЕ боевой базе**:
`arch_snapshots`, `arch_changes`, `arch_links` (карта), `arch_derived` (происхождение),
`arch_tools` (инструменты), `arch_diffs` (сверка), `arch_runs` (журнал проходов).
Плюс **правки «до» пишутся в САМУ таблицу `changes`** боевой базы с `kind='архив'` —
её скан не чистит (только дописывает), поэтому ранние правки остаются «в начале» хронологии.

Порядок записи — как у самого PLM Reader: **замок** → копия активной базы в `%TEMP%` →
вставка → `_publish` (бэкап + новый versioned-файл + ротация 3 + зеркала). Боевая база цела
до конца; перед записью — копия в `\\Backup\Public\АРХИВЫ\PLM_БАЗА\`.

## ИНСТРУМЕНТЫ И ПРИСПОСОБЛЕНИЯ В МАНУФАКТУРИНГЕ (03.10.2026, дополнение)

**Инструменты читаются чётко** (PLM Reader их не собирает):
- номера `T0001`, `T0010`… — вхождения литерала `T####` в MFG-файле;
- **имена** — значением `tool_id\0<имя>`: реальные названия (`CENTROVKA`, `DNMG55-TOK-R08`,
  `35-GRADUSOV-TOKARN,VNMG-35`);
- операции — `oper_info(wcell_info)` → `num_of_items`, `name` (`MILL01` = фрезерование).

**Приспособление — по словам хозяина:** это отдельная модель (деталь **или** сборка, имя
произвольное), которая добавлена в мануфакторинг **как компонент сборки**. Значит искать его по
суффиксу имени (`-PRISP`, `-FIX`, `-ОПОРА`) ненадёжно — в доме так называют не всё.

Что есть в файле MFG (`ASSEM_MFG`) по разбору байтов:
- `model_items_data` → `u_item` → `type`, `aux_type`, `id`, `aux_id` — элементы мануфакторинга;
- у каждого **компонента** есть блок `mfg_info_ptr … type … ref_id` — это его роль
  (деталь / приспособление / заготовка). Значение `type` — один байт;
- блок `fix_id` = функция оснастки (`node_val(func_call)`, `ext_func_id`, `height`,
  `balance_factor`), а не имя модели-приспособления;
- маркеров `fixture`/`workpiece` в файлах нет — тип хранится в `mfg_info_ptr.type`.

**Решение хозяина (03.10.2026):** собирать СЫРЫЕ данные — все компоненты сборок с их
`mfg_type`, а что считать приспособлением — хозяин разберёт сам. Поэтому:
- таблица `arch_mfg_items(arch_date, model, comp, mfg_type, is_fixture, note)`;
- таблица `arch_fixtures(arch_date, model, path, fixture, note)`;
- связи в `arch_links` с `kind='приспособление'`;
- просмотр: `arch_map.py --mfg` (сводка по типам, компоненты по сборкам, самые частые),
  `arch_map.py --tools` (инструменты).

**ГРАБЛИ разбора MFG:** `read_fixtures` сначала выдавал мусор (`rsd_alt_tbl`,
`node_val(op_code)`, `цсчyrel_model_name`) — из блока `fix_id` нельзя брать первое
похожее на имя; теперь берётся ТОЛЬКО имя, совпадающее с реальным компонентом сборки,
иначе приспособление считается незаданным (пусто — честный ответ).

### ⚠️ ВАЖНО (проверено 03.10.2026): байт `mfg_info_ptr.type` ≠ `ComponentFeat.GetCompType()`

В скилле `D:\AI\repo\Creo\READ\SKILL_creo_read_mfg.md` §5 указаны коды ролей компонента
мануфактурингa через **API Creo**: `0` заготовка, `1` ссылочная модель, `2` оснастка,
`10` стержень, `11` результат литья (оснастка ещё ищется по `FEATTYPE_FIXTURE_SETUP = 91`).

Чтением из файла это **НЕ подтвердилось**: на эталонной сборке
`df-stp2-gdf.asm.1` (1,2 МБ, состав: `DF-STP2-GDF-02`, `DF-STP2-GDF-03`, `INLBS_MFG_NC`
(оснастка по скиллу), `MFG_NC_NEW`, `SBORKA_MFG`) все компоненты дали `mfg_type = -1`,
а на других сборках — `-1` или `1`. Значит роль хранится не в том байте (или в другом
блоке данных компонента), и объявлять приспособление по нему **нельзя**.

**Поэтому в базе:** `arch_mfg_items.mfg_type` — это СЫРОЙ байт из `mfg_info_ptr`, в примечании
лежит лишь подсказка по таблице кодов; `is_fixture` ставится только по надёжным признакам
(сейчас их нет — приспособление по умолчанию не помечается). Чтобы пометить, нужен либо разбор
структуры компонента в секции сборки, либо контрольный опыт в Creo (назвать сборку и
приспособление, где хозяин точно знает, что это приспособление).

Из того же скилла полезно для нас: признак MFG-сборки — секция `NeuAsmSld` > 100 КБ
(у обычной сборки она пустая, 41 б); состав мануфактуринг-сборки по скиллу:
деталь + заготовка + `INLBS_MFG_NC.ASM` (оснастка) + `SBORKA_MFG.ASM` + `T0010.PRT`
(инструмент) + `HAAS_3X.ASM` (станок); CL-данные (траектории) в ПЛМ не собираем — берём
операции/переходы/инструмент.
