# ЧТЕНИЕ ФАЙЛОВ CREO «В ЛОБ» (файл напрямую, без Creo и CREOSON)

**Зачем:** не открывать Creo (тяжело, долго, занимает лицензию/железо), не мусорить в рабочих
папках (вариант «история → в файл» пишет HTML рядом с моделью), читать весь склад массово,
работать когда Creo закрыт. Приём проверен домом: таблицы семейств читались из файла ещё в Давыдовке.

## 1. История изменений («Инструменты → Исследовать → История файла»)
Данные лежат **внутри модели**, сервер не нужен. Найдены ДВА вида записи (Creo 12 и Creo 11):

**Раскладка A (Creo 12, `.asm` — проверено на `liteika_hts_mm.asm.1`):**
```
… <имя пользователя> \0  e2 | sec min hour_utc day (month-1) (year-1900) | f7 31 e3 | "РЕВИЗИЯ" \0\0
   <текст UTF-8> \0 … "Creo X.Y.Z.W" …
```
**Раскладка B (Creo 11, `.prt`):**
```
user_name \0 USER \0 … modif_time \0 (tm_sec tm_min tm_hour tm_mday tm_mon tm_year — по одному байту)
   … typed_data(MdlStored) \0 … rev_string \0 <номер> \0 … comment \0 <текст UTF-8> \0 …
```
**Формат времени:** однобайтовые `sec, min, hour, day, month-1, year-1900`; **время в файле — UTC**
(локальное КБ = UTC + 3). Проверка: LITEIKA `08:10:56 UTC` = `11:10:56` местного ✓.
**Тип операции:** `typed_data(MdlStored)` = «Модель сохранена» (в файле описан один раз в словаре типов).

ревизии **718 / 713 / 712 / 710 / 708**, пользователь `USER`, компьютер `frezer-4`,
05.08.2026 11:10:56 / 04.08 17:03:30 / 16:50:45 / 15:55:08 / 15:50:25 ✓
**Код (рабочий, обе раскладки):** парсер истории внутри `history()` в
`D:\AI\tools\agent\plm_reader\plm_reader.py` (окно + CLI; см. §8.25–8.27). Ранний прототип (только раскладка A)
остался в урне: `D:\AI\log\urn\cline\creo_history_v2.py`. Раскладка B сведена в общий парсер (проверено на
`.prt` Creo 11 — например `191-9050-gr4-1.prt.1`: 28 записей, дата 19.03.2025 11:11, Creo 11.0.2.0).

**Раскладка C (Pro/ENGINEER — старые записи):** версия хранится как `4.0` / `6.0` — БЕЗ слова «Creo»
(поле `Proe_version`), а компьютер — той же строкой «Наименование компьютера: 'FREZER-1'». Парсер,

**Универсальный якорь записи/изменения — маркер `f7 ?? e3 <ревизия> 00 00`** (`??` — байт типа);
к нему привязываются и записи истории, и записи изменений (к ближайшему предшествующему).

## 2. Таблицы семейств (проверено раньше, Давыдовка)
Секция `FamilyInf`, имена после тегов `e3`/`1f` — читается без сессии Creo и без загрузки исполнений

## 3. Грабли (дорого дались)
* **Текст — UTF-8, а строки интерфейса — cp1251.** Декодировать по факту, иначе «кракозябры».
* Имена полей — NUL-терминированный ASCII; между полями — бинарные метки и однобайтовые значения.
* **Ловушка:** в ASCII-дампе перед номером ревизии «видно `1\x00`» — на самом деле это часть бинарной
  метки `7e f7 31 e3`. Не искать ревизию по «тексту», искать по метке + ASCII-цифры + `00 00` + UTF-8 текст.
* Одно и то же имя поля встречается много раз (в файле `Наименование компьютера` — 198 раз, а реальных
  записей истории — 25). Фильтровать строго по метке записи.
* **История пишется не во все объекты** — зависит от настройки/обстоятельств сохранения. Пустая история
  не значит «файл битый». И отдельная ловушка: чертёж из `D:\AI\PROBA\23-1017GRI\test.drw` оказался
  **подделкой** — 19 байт текста `dummy drw content`; настоящие файлы опознаются по `#UGC:2`.

## 4. ЧТО ВООБЩЕ ЧИТАЕТСЯ — карта файла (25.09.2026)

**Уже подтверждено, что читается:**

## 6. УСТРОЙСТВО ФАЙЛА И ЧТО ЧИТАЕТСЯ ДОКАЗАННО (второй заход, 25.09.2026)

**Устройство:** заголовок `#UGC:2 <ТИП>` → **оглавление `#UGC_TOC`** (строки
`Имя <offset_hex> <len_hex> <len-10> 2572`, цепочка продолжается через `NEXT_TOC_ENTRY <offset> <len>`)
→ секции. В детали Сергея — **47 секций**: `BasicData` 87 836 б, `LargeText` 27 390, `AllFeatur` 21 802,
`VisibGeom` 19 729, `THMB_IMG_MAIN` 18 179 (**миниатюра модели!**), `FeatDefs` 15 095, `FullMData` 7 998,
`Notes`, `FamilyInf`, `MdlStatus`… **Адреса и длины лежат прямо в файле** — слепой скан не нужен.
Модуль-читатель: `D:\AI\log\urn\cline\creo_sections.py` (плюс `creo_diff.py` — сравнение версий).

**Записи — типизированные поля** `e0 <тип> <имя>\0 <значение>`: `01`=1 байт, `02`=2 байта (uint16),
`0a`=строка до `\0` (UTF-8, иногда UTF-16LE), `00`=ссылка/пусто, `03/04/09`=сырые байты.

**Доказанно читается «в лоб»:**
* **Технические требования / заметки** — секция `Notes`: 9 строк («Общий_случай_без_ТО», «размеры для справок;»,
  «Предельные отклонения по H12; h12;», «Неуказанные фаски- 0.5х45», «радиусы- R0.5 мм.») ✓
* **История (раскладка B)**: `user_name` → `modif_time` (`tm_sec/min/hour/mday/mon/year`, **UTC**) →
  `typed_data(MdlStored)` → `rev_string` («1223», «1224») → `comment` («Наименование компьютера: 'frezer-4'») →
  `Proe_version` («Creo 11.0.2.0») — **кто, когда, на каком компьютере, какой версией** ✓
* **Элементы** — имя + `feat_id` (`Вращение 1`, feat_id=3; поля `feat_id/geom_id/revnum`);
* **Отношения** — код + русские пояснения («…1000 /* 1->0, ; 10->0,1; … количество знаков после ","»);
* **Таблицы имён/слоёв/аннотаций** — `LargeText` (`RIGHT/TOP/FRONT`, `PRT_CSYS_DEF`, `AXES/NOTES/SOLID`,
  `num_feat_regens`, `saved_operation`, `SHOWN_ANNOTATIONS`);
* **Геометрия** — выровненные массивы float32 (координаты) в `VisibGeom/NovisGeom`;
* **Сравнение версий** (демо `.prt.1` vs `.prt.2`): **добавлены 8 требований** (H12/H14, фаски 0.5х45, R0.5),
  изменились размеры секций (`LargeText` +1401, `MdlStatus` +2292, миниатюра +685, `AllFeatur` −1) ✓

**Правка «в лоб» — можно, но с оговорками** (проверено на копии, оригинал не тронут): контрольной суммы
в шапке **нет** (ни crc32, ни сумма байт не дали 8-значный hex — это счётчик/идентификатор); правка **текста
той же длины** файл не ломает (заметка `Общий_случай_с_ТО` → `_ТР`: 47 секций, оглавление цело).
**Менять длины нельзя** — поедут адреса секций. Правки только на копии, с бэкапом и проверкой в Creo.

**Открытый вопрос:** **размеры**. Значений (40/150) нет ни как float32/float64, ни как обычный текст.
Найдено, куда смотреть: в `BasicData` числа лежат **в UTF-16LE** — видно `34 00 30 00` = «40» рядом с кусками
отношений (`floor`, `!=`, `)*`, `)-`). Значит искать размеры/текст нужно и в UTF-16LE, а не только в UTF-8.

### 7.1. ПОЛНЫЙ ЧИТАТЕЛЬ ИСТОРИИ — как в отчёте Creo (готово, проверено)

Запись = отметка «кто+когда» + хвост:
* отметка логина/времени: `f7 14 <логин>\0 e2 <6 байт UTC>` (Creo 11–12, детали) **или**
  `<логин>\0 e2 <6 байт UTC> f7…` (раскладка A: шаблоны, сборки);
* хвост записи: **`f7 <?> e3 <номер ревизии>\0\0 <"Наименование компьютера: 'X'">\0 <"Creo a.b.c.d">\0`**;
* рядом — имя модели: `f7 28 e2 <ИМЯ>`.

Скрипт: `log\urn\cline\history_full.py <файл…>` → таблица «дата (UTC) · ревизия · пользователь · компьютер ·
версия Creo · модель».

### 7.2. СВОЙ ПОЛНЫЙ ОТЧЁТ ОБ ИЗМЕНЕНИЯХ — `creo_change.py` («кто + что + было→стало + когда»)

Запуск: `python creo_change.py <версия1> <версия2>` — печатает:
1. **историю обеих версий** (ревизия · дата · пользователь · компьютер · Creo);
2. **± отметки «кто+когда»** — что именно добавило последнее сохранение и кем;
3. **± КОМПОНЕНТЫ сборки** — по записям `ID <номер> (<ИМЯ.PRT|.ASM>)` со счётчиками упоминаний;
4. **± ЭЛЕМЕНТЫ построения** (имя + `feat_id`);
5. **± ИМЕНОВАННЫЕ ОБЪЕКТЫ/ПАРАМЕТРЫ** (имена; значения — когда лежат рядом);
6. **± ЗАМЕТКИ/ТТ** (секция `Notes`);
7. **~ СЕКЦИИ** — что выросло/уменьшилось (топ по модулю).

### 8.1. Привязки сборки — что именно лежит в файле
Запись привязки называется **`place_instruction_ptrs`** (по числу компонентов; в проверенной сборке — 3).
Её поля (разобрано на `insert-stp-s1-iz-obrezkov-v4.asm.1`):
`local_sys`, `own_ref_id`, **`orient`**, **`type`**, **`offset`**, **`offset2`**, `dim_id`, **`ref_id`**,

`attr`, `plin_info_arr`, `step_ids`, `sub_feat_ids`, `ref_ids`, `trf_arr`, `transf`, `key`, `idx`.
**Что собираем:** какие два компонента и какие их поверхности/кромки сопоставлены
(`geometry1_id`+`memb_num1` ↔ `geometry2_id`+`memb_num2`), тип привязки (`type`), смещения
(`offset`/`offset2`), параметры `uv`, ориентация/флаг (`orient`, `flip`), система координат (`local_sys`,

Родственные ключи в файле: `attach_ptr_r22`, `named_orient`, `flip`, `matrix`, `coord`, `View`, `viewattr`.
**Не сделано:** словарь значений `type` (какой код = Совпадение/Выравнивание/Вставка/…) — следующий шаг.

**Наблюдаемый набор кодов (инструмент `place_types.py <asm…>`):** `type` = **155, 148, 143, 133, 130, 5**
(по 1–2 записи на сборку; в простых сборках — всего **2–3 привязки**). Примеры (из проверенных сборок):
```

type=148  orient=0  g1=246 g2=246  memb=0/0  id_type=—        offset=57368   ← без ориентации, g1=g2
type=143  orient=0  g1=128 g2=246  memb=1/0  id_type=5/245    offset=57368   ← у сборок с заготовкой
type=133  orient=0  g1=8   g2=246  memb=0/0  id_type=25/245   offset=57368
```

Гипотезы (нужен контрольный опыт): `130` — базовое сопряжение детали/заготовки (orient=1), `148` — фиксация/

### 8.18. КАЛИБРОВОЧНАЯ ТАБЛИЦА «ЗНАЧЕНИЕ → БАЙТЫ» (опыт Л, 12 точек)


### 8.19. ФОРМУЛА УПАКОВАННОГО ЧИСЛА CREO — ВСКРЫТА И ПРОВЕРЕНА (25.09.2026)

**Формат (для чисел ≥ 2, 3 байта):**
```
value = 2^(E+1) × (1 + F/4096)
E = старшая тетрада 2-го байта      F = (младшая тетрада 2-го байта << 8) | 3-й байт
1-й байт: 0x2F = положительное, 0x48 = отрицательное (у него мантисса та же)
```
**Проверка — 12 точек, ошибка 0.0000 %:** `2.0 → 2f 00 00`; `3.0 → 2f 08 00` (E=0,F=2048 → 2×1.5);
`4.0 → 2f 10 00`; `8.0 → 2f 20 00`; `10.0 → 2f 24 00` (E=2,F=1024 → 8×1.25); `16.0 → 2f 30 00`;
`16.5 → 2f 30 80`; `32.0 → 2f 40 00`; `64.0 → 2f 50 00`; `100.0 → 2f 59 00` (E=5,F=2304 → 64×1.5625);
`128.0 → 2f 60 00`; `1000.0 → 2f 8f 40` (E=8,F=3904 → 512×1.953125).

**Малые числа — короткие формы (1–3 байта):** `0.0 → 18`, `0.001 → 07`, `0.25 → 0d`, `0.5 → 0e`, `1.0 → 0f`
(1 байт); `0.125 → 2a c0 00`, `0.0625 → 2a b0 00` (3 байта, 1-й байт `2a`: для них `value = 2^(E−15)`,
проверено: `0.125` → E=12 → 2⁻³ ✓, `0.0625` → E=11 → 2⁻⁴ ✓). **Длина упакованного числа плавает 1–3 байта** —
именно поэтому поиск по фиксированным IEEE-узорам был обречён.

**Практика (инструмент `scan_packed.py <файл> [мин] [макс]`)**: сканирует файл и печатает все упакованные числа
в диапазоне. Проверка на реальной детали: в `.prt.2` (размер d9 = 17.0) найдено **108** вхождений `2f 31 00` = **17.0**;
в файле даже нашлась **таблица пар** упакованных чисел: `9.0/6.0 · 14.0/10.0 · 17.0/13.0 · 21.0/16.0 · 26.0/20.0 · 32.0/25.0`
(типоразмерные пары). В `.prt.3` (d9 = 16.123456) вхождений 17.0 осталось **17** — размер действительно переписан.

### 8.20. ТРИ ФОРМЫ УПАКОВАННОГО ЧИСЛА — ПОЛНЫЙ ДЕКОДЕР (проверено 25.09.2026)

Опыт Н (дробные значения параметра `CAL`) дал последние кусочки:

| значение | байты | форма |
|---|---|---|
| 16.0625 | `2f 30 10` | 3 байта (E=3, F=16 → 16×1.00390625) |
| 16.125 | `2f 30 20` | 3 байта (E=3, F=32 → 16×1.0078125) |
| **16.123456** | **`2d 30 1f 9a cf fa 7e b7`** | **8 байт — расширенная форма** |

**Формулы (все три формы):**
```
3 байта  [2f|48][E:F12]              value = ±2^(E+1) × (1 + F/4096)
8 байт   [2d][E:F12][5 байт дроби]   value = base + (frac5 / 2^40) × 2^(E+1)/4096   (полная точность)
1 байт   [..]                        короткие формы малых чисел (0.0→18, 0.001→07, 0.25→0d, 0.5→0e, 1.0→0f)
```
Проверка расширенной формы: `2d 30 1f 9a cf fa 7e b7` → base = 16×(1+31/4096) = 16.12109375;
frac5 = 0x9ACFFA7EB7/2⁴⁰ = 0.60471; шаг = 16/4096 = 0.00390625 → 16.12109375 + 0.60471×0.00390625 = **16.1235** ✓
(ровно 16.123456). В `.prt.29` (16.125) старое значение `2d 30 1f 9a cf fa 7e b7` тоже осталось —
в журнале изменения, как и у строковых параметров.

### 8.21. СТРУКТУРА ПОТОКА ЗАПИСЕЙ: ИСПРАВЛЕНИЕ «64 БАЙТ» И РЕАЛЬНЫЕ РАЗМЕРЫ (25.09.2026)

**Исправление:** ранее я написал «шаг записей ≈ 64 байта» — это была **планка моего алгоритма сравнения**
(окна диффа по 64 байта), а **не размер записи в файле**. Честный факт ниже.

**Измерено (`record_stat.py <файл> <секция>`, секция `AllFeatur`):**
* поток — **теговая байтовая лента**: частоты маркеров `f6`×749, `e2`×656, `e3`×602, `f5`×468, `e4`×369,
  `eb`×337, `f7`×333, `e0`×235, `e5`×208, `e1`×176, `e7`×123, `f2`×111 — то есть это внутренний p-code,
  где двубайтовые маркеры (`e0`–`f7`) чередуются со значениями;
* **`e3` — разделитель записей**: 878 штук, самое частое расстояние подряд — **10 байт (265 раз)**, далее 11, 9,
  7, 8, 3, 12, 6 → **типичная запись ≈ 10–12 байт**, а не 64;
* **`f1`/`f2`/`f3` делят группы покрупнее** (расстояния 30–200 байт, средние 180–290 б);
* **`eb` + 4 байта = метка времени/число** (5 байт), в изменениях видны пары таких меток (`eb 6a b6 33 14` …) —
  это `tstamp` пересчёта;
* при правке размера/параметра **секции пересобираются целиком** (в `AllFeatur` меняется блок ~15 000 б,
  в `LargeText` ~10 700 б) — поэтому побайтовый дифф «плывёт» и не годится для поиска изменений:
  нужен структурный разбор (типизированные поля + эти маркеры), а не попарное сравнение байтов.

  **размеры** (`typed_data(MTTyped_ModifyData)` → имена `d…`) и **параметры**
  (`chg_param_arr`/`param_typed_data` → имя). Изменение привязано к ближайшей предшествующей записи
  (маркер `f7 ?? e3 <rev> 00 00`). ЧИСЛА «было→стало» Creo в записи НЕ хранит (`old_val`/`new_val` пусты) —
  видно ИМЯ изменённого размера, а не значение.
* **`history()` обобщён**: старые записи Pro/ENGINEER хранят версию как `4.0`/`6.0` без «Creo» — раньше
  терялись (на `23-1017gri-01r.prt.1` было 15 записей, стало **28**; сводная история папки клапанов
  382 → **1202**). Регулярка версии: `((?:Creo )?[0-9][0-9.]*)`.
* **«Версии…»** (`version_diff` + `sibling_versions`): сравнение версий одного изделия рядом в папке
  (`.prt.1/.2/.3`, `…-04.asm.1/.2/.3`) — было→стало по ревизии/дате/объёму/габариту + что менялось по
  внутренним записям каждой версии; выгрузка в CSV (окно `versions_window`). Проверено на папке клапанов:
  `птр-401-17-kolco1.prt.1…4` ревизии 413→414→415→416; `…-04.asm.1…3` 394→406→409.
* **Габарит**: `outline_mm` отсеивает мусорные значения (вне 0.001…100000 мм) — в таблице больше нет
  `17866027888132623433728.0`; у части изделий габарит пуст (данные не записаны — копия без пересчёта).

Честное ограничение: **числовые «было→стало» по отдельному размеру** пока не читаются (Creo не пишет
значения в журнал; значения даёт сравнение версий — и то, если изделие пересчитывалось: объём/габарит).
У деталей без переопределений журнал изменений пуст (`parse_changes` = {}) — это не ошибка.

**Грабли доработки (нашли пробой, а не глазами):**

  Строки в окне были видны, и прошлая самопроверка окна дефект не поймала — **проверять не только
  таблицу, но и выгрузку**. Лечение: `extrasaction="ignore"` + столбцы из объединения ключей всех строк.
* `history()` терял старые записи Pro/ENGINEER (см. §1, раскладка C) — «наполнить максимально» это и вскрыло.
* Записи изменений привязываются к ревизии по ближайшему ПРЕДШЕСТВУЮЩЕМУ маркеру — если запись не
  распознана (как было с Pro/E), её изменения «повисают» и не показываются: парсеры истории и изменений
  обязаны согласованно видеть ОДИН и тот же набор маркеров.

### 8.31. `plm_tree` → ПОЛНЫЙ ПЛМ: требования и устройство (25.09.2026, замысел)

| **64.0** | `2f 50 00` | 3 |
| **100.0** | `2f 59 00` | 3 |
| **1000.0** | `2f 8f 40` | 3 |
| **−16.5** | `48 30 80` | 3 |

**Что из этого следует:**
* **Длина упакованного числа ПЛАВАЕТ: 1 байт (0.0, 0.001, 0.5, 1.0) ↔ 3 байта (0.125 и все ≥ 2)** — поэтому поиск по
  фиксированным IEEE-узорам не мог сработать в принципе.
* **Знак — в первом байте**: `16.5 → 2f 30 80`, `−16.5 → 48 30 80` (мантissa `30 80` идентична, меняется только
  первый байт).
* **Дробная часть — младший байт**: `16.0 → 30 00`, `16.5 → 30 80` (добавка ровно `80` за 0.5).
* **Мантissa растёт логарифмически** (старшая тетрада ≈ log2 − 1: 2→`0`, 4→`1`, 16→`3`, 64→`5`, 100→`59`,
  1000→`8f 40`) — это **hex-подобная экспоненциальная упаковка**, а не IEEE. Точную формулу добьём точками
  3.0, 8.0, 32.0, 128.0, 0.25, 0.0625.
* Значение дублируется в файле: `NeuPrtSld` (`<имя>\0 e2 32 <байты>`) и `LargeText`
  (`<имя>\0 27 88 00 e3 32 <байты>`, плюс `f7 1d e3 32 <байты>`).
* Батч-установка параметров даёт `Pro/TOOLKIT General Error` — ставить по одному с паузой ≈1.5 с.
