# SKILL: МЕТА-ЗАПИСИ (META-RECORDS) И СВЯЗКИ СЕКЦИЙ (e1 f1)

**Назначение:** Понимание того, как Creo связывает логические структуры (например, вкладки сборки, таблицы семейств или указатели на таблицы драйверов) с физическими секциями файла.

## 1. ПАТТЕРН МЕТА-ЗАПИСИ (e1 f1)

В некоторых критических полях (например, `drv_tbl_ptr`, `ref_part_tab`) значением является не прямой указатель на адрес в ОЗУ или смещение, а **мета-запись**.

**Структура:**
```
<marker e1> <type_code f1> <sub-records separated by e3>
```

**Особенности:**
1. **Разделитель `e3`:** Внутри мета-записи байт `0xe3` используется как разделитель под-записей (sub-records), в отличие от его основной роли как разделителя записей в потоке файла.
2. **Логическая связь:** Мета-запись служит «мостом». Она содержит идентификаторы (часто текстовые или полу-текстовые), которые соответствуют именам физических секций (`#SectionName`).
3. **Пример разбора (на основе 00080-03.prt):**
   - Поле: `drv_tbl_ptr\0`
   - Значение (Meta-Record): `e1 f1 #\n#VisibGeom\n`
   - Цель: Указывает, что следующая важная секция — это `Sld_VisGeom` (через текстовый маркер `#VisibGeom`).

## 2. ПРИМЕРЫ И СЛУЧАИ

### Случай А: Связка с VisibGeom
- **Поток:** `...drv_tbl_ptr\0` $\to$ `e1 f1` $\to$ `#\n#VisibGeom\n` $\to$ `e0 00 Sld_VisGeom`.
- **Смысл:** Поле `drv_tbl_ptr` не содержит адрес, оно содержит «инструкцию» найти секцию `VisibGeom`.

### Случай Б: Сложные мета-записи
- **Поток:** `e1 f1 <data> e3 <data> e3 <name>\0`.
- **Смысл:** Позволяет хранить несколько связанных идентификаторов или параметров в одном логическом блоке.

## 3. АЛГОРИТМ РАЗБОРА

1. Если после поля (например, `drv_tbl_ptr`) обнаружен маркер `e1` и тип `f1` — переключиться в режим чтения **Meta-Record**.
2. Считывать байты до следующего маркера (`e0..ff`) или до конца секции.
3. Разбить полученный блок по байту `0xe3`.
4. Для каждого под-блока определить:
   - Является ли он строкой (ASCII/cp1251).
   - Является ли он техническим идентификатором (начинается с `#`).
5. Использовать полученные строки для сопоставления с ближайшими физическими секциями `#SectionName`.

## 4. ГРАБЛИ
- **Не искать смещения:** Попытка интерпретировать `e1 f1 ...` как `double` или `int` приведет к ошибке. Это структурный блок.
- **Игнорирование `e3`:** Если не учитывать `e3` внутри `e1 f1`, мета-запись будет прочитана как один длинный мусорный блок.

## 5. ВЕРИФИКАЦИЯ (Stage 6)
Прогон `creo_raw_inspector.py` подтвердил корректность извлечения имен полей из мета-записей `e1 f1` даже при наличии разделителей `\0` или `e3`.

**Результаты:**
- `base-with-4holes.prt`: найдены `drv_tbl_ptr`, `sym_bak_rstr`, `pmech_data`, `neut_assem`.
- `00080-03.prt`: найдены `table_name`, `description`, `color_prop`, `drv_tbl_ptr`, `neut_assem`, `piping_info`, `mdl_ids_info_db`, `embed_info_ptr`, `p_ply_data`.

## 9. БАЙТНЫЕ ПРАВИЛА РАЗМЕТКИ

На основе бинарного анализа файлов `00080-03.prt` и `base-with-4holes.prt` проверены следующие байтовые контракты:

1. **Счётчики**
   - Длина каждой секции (включая заголовок) хранится как 16‑битное беззнаковое целое (`uint16`) в **big‑endian** порядке непосредственно перед маркером секции `#SectionName`.
   - Пример (смещение 0x658f): `0x00 0x65` → длина 165 байт для блока `FamilyInf`.
   - Тот же шаблон встречается для `drv_tbl_ptr` (длина 0x00 0x4b) и `table_name` (длина 0x00 0x4b).

2. **Выравнивание**
   - После счётчика длина выравнивается до 4‑байтовой границы, когда следующий элемент – 32‑битное целое.
   - Паддинг‑байты `0x00` не считаются «мусором», они гарантируют выравнивание следующего `type_code` (`e0…ff`) на 4‑байтовую границу.
   - Для 64‑битных полей (например, `e0 02` double) выравнивание до 8 байт; скрипт выравнивает до ближайшей 8‑байтовой границы.

3. **Коды типов**
   - Байт после счётчика (`e0…ff`) кодирует тип поля:
     - `e0` – 64‑битное число с плавающей запятой (IEEE‑754, big‑endian)
     - `e1` – начало мета‑записи (`e1 f1 … e3` разделитель)
     - `e2` – 32‑битное целое (знаковое, big‑endian)
     - `e3` – завершитель строки или маркер секции.
   - Код **не** является длиной имени; это фиксированный идентификатор.

4. **Имя поля**
   - Имя поля следует за кодом типа как NUL‑терминированная ASCII‑строка (максимум 64 байта). Пример: `drv_tbl_ptr\0`.
   - Имя чувствительно к регистру и может содержать подчеркивания.

5. **Значение**
   - Значение занимает количество байтов, указанных типом:
     - Для `e0` (double) – 8 байт.
     - Для `e2` (int32) – 4 байта.
     - Для мета‑записи (`e1 f1`) – переменная длина, завершающаяся `0x00` или следующим маркером секции.
   - Байты значения интерпретируются согласно типу; они никогда не являются «мусором».

6. **Начало секции (`#SectionName`)**
   - Маркер `#SectionName` появляется после значения предыдущего поля, предшествующего счётчику длины (uint16) и коду типа `e0` (или `e2` для целочисленных секций).
   - Имя секции – ASCII, NUL‑терминированная, может начинаться с префикса `Sld_` для твердых секций.

Эти правила заменяют прежнюю гипотезу «любой байт, не являющийся печатным, – мусор». Каждый байт имеет определённую роль, как показано в hex‑дампe `00080-03.prt` (см. вывод скрипта). Скрипт `byte_map.py` выводит точную разметку полей `drv_tbl_ptr`, `table_name`, `description` и `#FamilyInf`.
