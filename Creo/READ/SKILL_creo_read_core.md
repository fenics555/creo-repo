# ЯДРО: КАК УСТРОЕН ФАЙЛ CREO (все части чтения держатся на этом)

## 1. КОНТЕЙНЕР И ТИПЫ
Каждый файл начинается строкой вида `#UGC:2 <ТИП> …`. Типы, которые реально встречаются:
`PART` · `ASSEMBLY` · `ASSEMBLY/ASSEM_MFG` (мануфакчуринг) · `DRAWING` · `MFG_TOOL_PATH` (`.tph`)
· `PART/SHEETMETAL` · `PART/BULK`.
Затем текстовый заголовок `#- VERS / HOST / LINK / DBID / REVS / RELL / UOBJ_ID / MACH … #-END_OF_UGC_HEADER`.
⚠️ Настоящий файл опознаётся по `#UGC`; «подделка» (`dummy drw content`, 19 байт) — не файл.

**Два поколения** (различать при разборе!):
* `PART 2572 2120 804 … 2025323` — **Creo 11–12**, самая полная история;
* `PART 1991 1660 804 … 2021164` — **Creo 8-era**, оглавление другое: `BasicData 2883 156bd … 1991 …`.

## 2. СЕКЦИИ И ОГЛАВЛЕНИЕ `#UGC_TOC`
Оглавление — список `имя смещение(hex) длина(hex) …`. **Смещения не от начала файла** — секцию ищут
по маркеру `#Имя`, длину берут из оглавления.
Реальный набор секций детали (проверено, 32 секции на `din933.prt.1`):
`ActEntity, AllFeatur, BasBasData, BasFullData, BasicData, BasicText, DispCntrl, DwgData, FamilyInf,
FeatDefs, FeatDefsIndex, FullMData, GeomDepen, Geomlists, LargeText, MdlRefInfo, MdlStatus, MechanicaData,
NeuAsmSld, NeuPrtSld, Notes, NovisGeom, PipeInfos, SolidPersistTable, SolidPrimdata, VisibGeom, Xsections`
(+ технические `ND:…`, `NEXT_TOC_ENTRY`).

**Зачем деталь**: где что искать. Частота секций — быстрый признак типа модели
(`FamilyInf` 95 КБ = семейство; `Notes` = техтребования; `NeuAsmSld` = сборка).

⚠️ **Баг, стоивший времени:** маркер секции искать **точно** (`\n#Имя[\r\n]`), иначе `FeatDefs`
матчится с `FeatDefsIndex` и срез берётся не из той секции. Позиция содержимого = маркер + `len(имя)` + 1.

Проверенные признаки по типу файла:
* **`.prt`** → `NeuPrtSld` 21 КБ (параметры), `NeuAsmSld` **41 б** (пусто);
* **`.asm` (мануфакчуринг)** → `NeuAsmSld` **126 991 б** (параметры ЧПУ!), `NeuPrtSld` 41 б;
  шапка: `#UGC:2 ASSEMBLY/ASSEM_MFG 2350 1960 804 …`;
* семейство → `FamilyInf` 95 КБ; техтребования → `Notes`.

## 2б. ⚡ ЗАКОН ПОЛЯ — база любого разбора (вскрыт 03.10.2026, проверено на 2 моделях)
```
<tag e0…ff> <тип> <имя_поля>\0 <значение…>
```
| Тип | Значение |
|---|---|
| `01` | 1 байт (id, флаги) |
| `0a` | **строка** UTF-8 до NUL (имена объектов и операций!) |
| `02` | число / упакованное |
| `00` | ссылка / пусто |

Парсер: `re.finditer(rb"[\xe0-\xff][\x00-\x0f]([A-Za-z][A-Za-z0-9_/\.]{1,60})\x00", chunk)`.
**Почему это важно:** прежние поиски «по ASCII-маркерам операций» давали ноль — **имён операций в ASCII
в файле нет**, они лежат в строковых полях типа `0a` (см. `SKILL_creo_read_feat.md`).

Поля-ориентиры (встречены и проверены): `feat_id` · `feat_name` · `object_name` · `long_name` · `name` ·
`own_ref_id` · `new_id` · `type` · `attributes` · `gen_info` · `radius`/`radius2` · `flip` · `orient` ·
`local_sys` · `outline` · `parent_child_table` · `parchild_table` · `copy_info_ptr` · `gsec_ptr` · `is_ref_gsec`.

## 3. ЧИСЛА — ТРИ ФОРМЫ (главная ловушка)
| Форма | Вид | Пример |
|---|---|---|
| **BE-double IEEE** | `e0 02 <имя> 00 ed <8 байт>` | `volume`, `mtrl_volume` |
| **упакованная 3 байта** | `[2f\|48][E:F12]` | `16.5 → 2f 30 80`; знак в 1-м байте |
| **расширенная 8 байт** | `[2d][E:F12][5 байт дроби]` | `16.1235 → 2d 30 1f 9a cf fa 7e b7` |
| короткие малые (1 б) | `18`=0.0, `07`=0.001, `0d`=0.25, `0e`=0.5, `0f`=1.0 | |

**Формула 3-байтной:** `value = 2^(E+1) × (1 + F/4096)`, где `E` = старшая тетрада 2-го байта,
`F` = (младшая тетрада 2-го байта << 8) | 3-й байт. 8-байтовая: `base + (frac5/2^40) × 2^(E+1)/4096`.
⚠️ **Длина плавает 1–3 байта** → поиск по фиксированным IEEE-узорам принципиально не работает.
Декодеры дома: `packed_decode.py`, `scan_packed.py`, `decode_reals.py`.

## 4. ИСТОРИЯ ИЗМЕНЕНИЙ (внутри файла, сервер не нужен)
Три раскладки:
* **A (Creo 12)**: `<пользователь> \0 e2 <6 байт UTC> f7 ?? e3 <ревизия> \0\0 "…" \0 <текст UTF-8>`;
* **B (Creo 11)**: `user_name \0 … modif_time \0 typed_data(MdlStored) \0 rev_string \0 comment \0 Proe_version`;
* **C (Pro/ENGINEER)**: версия как `4.0`/`6.0` **без слова «Creo»** — парсер, ждавший строго `Creo X.Y`,
  терял такие записи (на `23-1017gri-01r.prt.1` было 15 из **28**). Правильное условие: `((?:Creo )?[0-9][0-9.]*)`.

**Время в файле = UTC** (местное КБ = UTC+3). Формат: `sec, min, hour, day, month−1, year−1900`.
**Универсальный якорь записи:** `f7 ?? e3 <ревизия> 00 00` — к нему привязываются и история, и изменения.
**Метка «кто+когда» по объектам:** `f7 14 <логин> \0 e2 <6 байт>` **или** `e1 f6 e1 <USER> 00 e2 <6 байт>`
(вторая раскладка дала +69 % покрытия дат; третья, ~31 %, не разобрана).

## 5. ПАРАМЕТРЫ
Запись: `<имя> \0 e2 33 <значение> \0`; **системные**: `PTC_*`, `PRO_MP_*`.
⚠️ Грабля §8.76: за значением идёт служебный префикс `\xf7 <1 байт>` — его надо отбросить (иначе «ч&UNCX01»).
⚠️ Имя не матчить как хвост длинного имени: `NAME` найдётся внутри `PTC_MATERIAL_NAME` (отсюда вместо
наименования приходит материал). Признак имени — **предыдущий байт не `[A-Za-z0-9_]`**.
Читать по **ВСЕМУ файлу** (не только `NeuPrtSld`): выигрыш материал +7 %, наименование +5 %, обозначение +4 %.

## 7. ПРАВИЛА РАЗБОРА
1. Текст — UTF-8; строки интерфейса — cp1251 → декодировать по факту.
2. Имена полей — NUL-терминированный ASCII; между полями бинарные метки.
3. Одно имя поля встречается сотни раз (`Наименование компьютера` — 198 раз при 25 записях) → фильтр **строго по метке**.
4. При правке размера секции **пересобираются целиком** (`AllFeatur` меняется блоком ~15 000 б) →
   побайтовый дифф «плывёт», нужен структурный разбор.
5. Поток записей — теговая байтовая лента; `e3` = разделитель записей, типичная запись **10–12 байт**
   (не 64: «64» — ширина окна моего диффа, не размер записи).
6. **Пустая история ≠ битый файл** — бывают копии, ни разу не регенерированные (правило владельца).
