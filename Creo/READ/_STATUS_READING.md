## Остаётся непрочитанным — и почему честно

1. **Ассембли без массы** — у сборки нет собственной массы, она суммируется из компонентов.
   Не дефект чтения.
2. **Пустые шаблоны библиотеки** — нет геометрии, нечего считать.
3. **BOM 0,3%** — 220 из 245 боевых сборок `ASSEM_MFG` физически не содержат BOM.
4. **Дерево — связка найдена, но плоская.** В `FeatDefs` (1.2 МБ) запись фичи
   выглядит так: `c0 <feat_id> f6 02 e3 <байт> 49 c0 <owner>`.
   **284 пары «фича → владелец» извлекаются устойчиво, 71 владелец имеет
   несколько детей.** Плюс в `MdlStatus` флаг `0x01` = заголовок группы:
   422 записи, 104 заголовка, 317 листьев, 0 пустых групп.
   **Осталось:** глубина связки = 1, корней = 0 — владелец сам не имеет владельца,
   то есть **вложенность групп теряется**. Прежняя эвристика
   «последняя открытая группа» пока ещё нужна для глубины.
5. **Координаты** — числа правдоподобны, но границы записей и XYZ-триплеты не доказаны.

### 1в. ✅ РАЗМЕРЫ ЧИТАЮТСЯ (05.10.2026, подтверждено эталоном)

Раньше значилось «размеры не читаются» — это **неверно**, как и с объёмом.

Структура значения размера в файле (эталон `a887-94-1500-01.prt.1`, смещение ~206300):

```
f1 f7 37 e3 32 <3 байта значения>  …  f2 f7 38 "d12" 00
```

**Формула числа: `2^(E+1) × (1 + F/4096)`**, где
`E = b[1] >> 4`, `F = ((b[1] & 0x0F) << 8) | b[2]`.

⚠️ **Маркер первого байта может быть ЛЮБЫМ** (`2f`, `2e`, `f7` …) — проверять только
`2f`/`48`, как в старых гипотезах, **нельзя**: это и сбивало разбор.

✅ Сверка с эталоном (хозяин смотрел в Creo):

| d13 | 21.5 | 21.5000 ✅ |
| d25 | 12.7 | 12.6992 ✅ |

⚠️ **Покрытие пока 13 %** (39 из 311 боевых файлов): в остальных размеры лежат иначе.

### 1б. Габарит — прогресс разбора (04.10.2026, не закрыт)

Запись `outline` живёт в секции **`BasicData`** (у эталона — `@+583` от начала секции).
Декодер 8-байтового числа **уточнён**: `F` — это **12 бит**, а не 4:

```
[маркер 2d|2f|46|48][E:F12][5 байт дробной части] = 2^(E+1) * (1 + (F + frac/2^40)/4096)
                     F = ((b[1] & 0x0F) << 8) | b[2]
```

Раньше F брали как 4 бита — из-за этого выходило 16.02 вместо 21.5.

✅ **Форма подтверждена на живых деталях:**
- `137_011_0041.prt.1` (`KRUG-43`) → числа **21.505 / 21.500 / −21.505 / −21.500** → диаметр **43** ✅
- `a887-94-1500-01.prt.1` (болт) → **76.200** (3 дюйма) и **21.500** ✅

⛔ **Но сама последовательность в `outline` — не bounding box.** На деталях
`23-1017gri-*` из тех же байтов выходят числа 266.85 / 145.49 / 86.80, что габаритом
не являются. Похоже, там лежит **список точек контура**, а не 6 чисел min/max.
Разбор последовательности **не закончен**.

→ Вывод: габарит пока **не пишем** (лучше пусто, чем мусор). Следующий шаг: снять эталонный
габарит из Creo на 2–3 деталях и сопоставить с последовательностью байтов.
`PRO_MP_MASS` встречается **19 раз**, байтовых хвостов — **2 разных**:
```
53 00 3D F5 EB 7E D5 27
53 00 F8 01 F7 38 FB E3
```
Значение **пересчитывается** при каждой правке. Правила «ведущий байт =
0x40/0x3F/0x41» не существует: нет фиксированной константы.
`null` — **окончательное** решение, не временное.
