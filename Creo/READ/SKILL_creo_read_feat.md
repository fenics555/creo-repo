## 0.1. ВСКРЫТЫЙ ЗАКОН ПОЛЯ (это база всего разбора)

```
<tag e0…ff> <тип> <имя_поля>\0 <значение…>
```
* `тип 01` → 1 байт (id/флаги) · `тип 0a` → **строка** (имя!) · `тип 02` → число/упакованное · `тип 00` → ссылка.
* **Имя операции = строковое поле `name` / `feat_name` / `object_name` / `long_name` с типом `0a`.**
  Это и есть причина прежних «0 операций»: искали ASCII-маркеры `Extrude`/`Sketch` — их в файле **нет вовсе**,
  тип операции хранится **не текстом**.
* Парсер: `re.finditer(rb"[\xe0-\xff][\x00-\x0f]([A-Za-z][A-Za-z0-9_/\.]{1,60})\x00", chunk)`.
* ⚠️ **Баг проб, стоивший времени:** `section("FeatDefs")` матчится с `#FeatDefsIndex` → срез секции неверный.
  Искать маркер **точно**: `\n#Имя[\r\n]`. Плюс база отсчёта = маркер + `len(имя)` + 1.

## 2. ✅ ГДЕ ЛЕЖАТ ИМЕНА (три секции — не одна!)
| Секция | Что там | Признак |
|---|---|---|
| **`MdlStatus`** | имена операций + история правок | `feat_id\0 … f7 29 e2 <ИМЯ>`, рядом `USER\0 e2`, `SER\0 e2` |

**Закон записи операции (по байтам):**
```
f7 49 | 84 8a | 05 84 80 | "Вытягивание 1" 00 | 84 8a | 84 8a | 00
        ^ID?      ^смещ.      ^ИМЯ (UTF-8)          ^ID повторён
```

## 2в. ⚠️ ВАЖНО: ОДНО ИМЯ В РАЗНЫХ СЕКЦИЯХ = РАЗНЫЕ СУЩНОСТИ (03.10.2026)
Проверено на `23-1017gri-01.prt.1`: «Вытягивание 9» встречается в `MdlStatus` **рядом с историей правки**
(`f7 14 ADMIN\0 e2 …`, `USER\0 e2 …`) — то есть это **запись в журнале «что менялось»**, а не описание фичи.
В `MdlRefInfo` то же имя лежит в записи `f7 49` — это **ссылочная геометрия** (`ref_model`,
`inherit_rep`, `p_foreign_source`).
`FeatDefs` — третий слой (свойства/определения).

**Вывод:** нельзя просто «собрать все кириллические строки» — надо **различать секции по назначению**:

| Секция | Что там на самом деле |
|---|---|
| `MdlStatus` | **журнал правок**: имена операций + кто/когда (`ADMIN`, `USER`, `SER`) |
| `MdlRefInfo` | **ссылочная геометрия**: фичи-источники, `feat_name`, `own_ref_id`, `inherit_rep` |
| `FeatDefs` | **определения/свойства**: `Сечение 1`, `Эскиз 1` + `type` |
| `NeuPrtSld` / `NeuAsmSld` | **параметры** (числа `e2 32`, текст `e2 33`) |

⚠️ Поэтому прежнее «29 уникальных операций модели» — это **смесь трёх разных сущностей**,
а не дерево построения. Считать дерево по этим именам нельзя.

## 3в. ⚠️ ЧИСЛО ПОСЛЕ ID — НЕ ТИП ОПЕРАЦИИ (проверено)
Гипотеза «байт после ID = `pfcFEATTYPE`» **не подтвердилась**: у одного и того же `Сечение 1` значения
разные (`f8 09`, `f8 03`, `f8 0a`), а у `Вытягивание 1` — `f8 06` с массивом из **7** id при `N=6`.
Значит `f8 <N>` — это **размер массива связей**, а не тип.

**Что остаётся искать тип:** поле `type` в `FeatDefs` (`e0 01 type\0 <значение>`). Проверенные значения:
`2` (→ `FEATTYPE_SHAFT`), `5` (→ `FEATTYPE_SLOT`), `193` (→ `FEATTYPE_HULL_WLD_FLANGE`).
Словарь из 280 позволяет проверять любое число → **долг №7 остаётся**, но теперь есть метод сверки.


`Сечение 1` → рядом поле `e0 01 type\0` со значением `5`.
Надёжных значений пока мало — **словаря типов нет** (долг №7). Гипотеза: числа кодируют класс операции
(5 = сечение/эскиз-подобная), но **не проверена на 10+ значениях** — не считать законом.

## 4. ⚠️ ЧТО ОСТАЛОСЬ НАЙТИ (данные в файле ЕСТЬ — нужен верный ключ)
Раньше здесь стояло «дерева нет». **Это было неверно** — по заголовкам API (§0.2) дерево есть и хранится
связкой `feat_id` ↔ `BeforeFeat/AfterFeat`. Проверено наблюдением (§3б): **ID-подобные байты `84 <id>`
лежат прямо рядом с именем операции**, диапазоны совпадают с `feat_id`:

| Файл | Извлечено ID | Диапазон | Уникальных ID в окне |
|---|---|---|---|
| `din933.prt.1` | 8 записей операций | **119..191** | 39 |
| `23-1017gri-01.prt.1` | 28 записей | **0..254** | 55 |

Осталось довести до дерева:

| # | Задача | Как искать |
|---|---|---|
| A | **число типа** | искать `84 <0..279>` непосредственно рядом с `84 <id>` и сверять со словарём из 280 |
| B | **связи «до/после»** | цепочки id в `AllFeatur`/`MdlStatus`: записи вида «id → before_id → after_id» |
| C | **ASCII-типы** | их в файле **нет** (`Extrude`/`Sketch` = 0) — тип только числом, это не потеря данных |
| D | **порядок регенерации** | `OnBeforeRegen/OnAfterRegen` → журнал в файле; иначе порядок байтов ≈ порядок построения |
| E | **лидеры групп** | `GetGroupLeader/GetPatternLeader` → записи с общим id и ссылкой на лидера |

⚠️ **Честная оговорка про ID:** текущая проба (`deep_chain.py`) берёт ID эвристикой «средний `84 xx`
в окне ±140 байт» — поэтому в списке есть дубли одного имени (напр. «Вытягивание 1» с ID 123/125/128/170).
**Для настоящего дерева нужен точный разбор записи**, а не эвристика. Инструмент: `deep_chain.py`.

## 3б. ✅ ID ОПЕРАЦИЙ ЛЕЖАТ РЯДОМ С ИМЕНЕМ (проверено на 2 моделях)
Сырой байтовый вид записи (из `din933.prt.1`, секция `MdlRefInfo`):
```
f7 49 | 84 8a | 05 84 80 | "Вытягивание 1" 00 | 84 8a | 84 8a | 00
        ^ID=138  ^?  ^смещ  ^ИМЯ (UTF-8)        ^ID=138  ^ID=138
```
ID объекта (`0x84 0x8a` = **138** у «Вытягивание 1», `0x84 0xab` = **171** у «Вытягивание 2»)
**повторяется до и после имени** — это устойчивый идентификатор записи.
**Ключ:** значение байта после `84` = число, а сам `84` — тег. Диапазон 0..254 согласуется с
`feat_id` (`wfcFeature::GetFeatureId()` → `xint`).
**Значит:** дерево строится как **граф по этим id**, а не как список имён.
