# ГЛУБОКИЙ АНАЛИЗ СЕКЦИИ FeatDefs (Опыт 19.10.2026)

Данный файл содержит результаты реверс-инжиниринга секции определений признаков (Feature Definitions) в бинарных файлах Creo.

## 1. Обнаружение и сегментация

Секция `FeatDefs` содержит набор записей, каждая из которых описывает один инженерный признак (feature).

### 1.1. 🔴 ДЕЛИМИТЕР `FB E3 F7 80` — ОПРОВЕРГНУТ ЗАМЕРОМ 28.10.2026

**Было написано:** записи разделяются паттерном `FB E3 F7 80` (`\xfb\xe3\xf7\x80`).
**Это НЕВЕРНО.** Проверка на живом файле `ctkd_015_23_001.prt.1` (модель, у которой
**эталон Creo дал 19 элементов**):

```
паттерн FB E3 F7 80: 97 вхождений -> split даёт 98 частей
```

**97 ≠ 19** — значит `split` по этому паттерну режет **не по фичам**, а по внутренним
сегментам. Второй скилл (`Creo\SKILL_creo_bit_level_anatomy.md`) был прав:
`FB E3 F7 80` помечен как **LOW / ЛОЖНЫЙ делимитер**, «не использовать для построения дерева».
Это расхождение двух скиллов от 19.10.2026 закрыто в пользу `bit_level_anatomy`.

**Правильно (по `bit_level_anatomy`, принцип «KEYS OVER WINDOWS»):** искать **КЛЮЧИ**
(`type\x00`, `ref_id\x00`, `sub_feat_id\x00`, `parent_id\x00`) и читать значение сразу за ключом;
и **русские имена операций** — они лежат в файле текстом (см. `SKILL_creo_read_feature_types.md`).

**Замер того же файла (текстом, 28.10.2026):** `ВЫТЯГИВАНИЕ` 9 · `СКРУГЛЕНИЕ` 4 ·
`ВРАЩЕНИЕ` 1 · `Тело` 1 · `ОПОРНАЯ ПЛОСКОСТЬ` 31. Английские коды (`cutextrude`,
`featround`, `dtmplane`) в файле Creo 13 — **0 вхождений**.

**Проверка расхождения:** сколько частей даёт `split`, обязано совпадать с числом элементов
из эталона (`tree_probe.bat`, см. `SKILL_creo_tree_jlink_etalon.md`).
Не совпало — делимитер ложный.

## 2. Внутренняя структура записи

Каждая сегментированная запись представляет собой смесь текстовых идентификаторов и числовых данных.

### 2.1. Текстовые данные (Strings)
Внутри записи присутствуют строки, выполняющие следующие роли:
- **Идентификатор признака**: Строки вида `feat_defs_<ID>` (например, `feat_defs_949`). Это ключевой маркер для восстановления дерева признаков.
- **Технические атрибуты**: Ключевые слова, описывающие свойства (например, `local_sys`, `orient`, `trf_arr`, `type`, `sub_type`).
- **Метаданные**: Имена параметров или связей.

### 2.2. Числовые данные (Doubles)
Геометрические параметры (размеры, координаты, углы) хранятся в формате:
- **Тип**: IEEE 754 Double Precision (8 байт).
- **Порядок байтов**: Big Endian (`>d`).
- **Характеристики**: Значения обычно находятся в логичном инженерном диапазоне (не zero, не NaN, не inf).

## 3. Алгоритм извлечения (Heuristics)

Для автоматического разбора использован следующий подход:
1. **Сегментация**: Разделение блока `FeatDefs` по паттерну `FB E3 F7 80`.
2. **Парсинг строк**: Поиск строк длиной > 3 символов.
3. **Идентификация Feature ID**: Поиск паттерна `feat_defs_(\d+)` в строках.
4. **Парсинг Doubles**: Сканирование 8-байтовых интервалов на наличие валидных вещественных чисел.
5. **Корреляция**: Сопоставление найденного `ID` с ближайшими к нему значимыми `Doubles`.

## 4. Наблюдения и "Грабля" (Важно!)

### 4.1. Стабильность TOC (Table of Contents)
- **Header Stability**: Строка `#UGC_TOC` (структура заголовка) остается **идентичной** (стабильной) во всех версиях Creo (от 6 до 12).
- **Offset Instability**: Несмотря на стабильный заголовок, **смещения (offsets) секций меняются радикально** от версии к версии.
- **ВЫВОД**: Нельзя использовать жестко заданные смещения для доступа к любым секциям. **Всегда парси TOC перед чтением любой секции**.

### 4.2. Резонанс данных
- Неправильное чтение (не по смещению из TOC) приводит к получению "мусорных" doubles из текстовых блоков.
