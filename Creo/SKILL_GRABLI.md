# SKILL_GRABLI: Lessons Learned

## Python Regex & Binary Data
- **Problem**: `re.PatternError: incomplete escape \x0 at position N`.
- **Cause**: Using literal `\x0` in a regex string in Python causes the parser to fail because it expects a two-digit hex code after `\x`.
- **Solution**: 
    - Use direct byte searching (`bytes.find()`) for locating keys.
    - If regex is absolutely necessary, use `re.escape()` or double-escape the sequence, or better yet, avoid raw byte escapes in the pattern string.
    - For binary data, work with `bytes` objects and avoid decoding until the value is isolated.

## Tooling Limitations
- **Editor**: When `editor` fails to replace text due to `old_text` mismatches or encoding issues, switch to creating a new file (e.g., `filename_vX.py`) to ensure a clean state.
- **Shell Encoding**: Be cautious with Cyrillic paths in shell commands. Use absolute paths and ensure encoding is handled correctly.

## ❌ КРИТИЧЕСКИЕ ОШИБКИ (Обновлено: 23.10.2026)

### 1. ПЕТЛЯ ПОИСКА (Search Loop)
- **Проблема**: Попытка найти ID через `Select-String` (текст) $\rightarrow$ `search_int` (число) $\rightarrow$ `regex` (паттерн) без изменения глубины анализа.
- **Симптом**: Инструменты возвращают 0 результатов, и агент продолжает вызывать их с другими паттернами.
- **Решение**: Если 3 попытки разными инструментами дали 0, СМЕНИТЬ МЕТОД. Переходи от «поиска значения» к «анализу структуры вокруг ключа».

### 2. ЛОЖНЫЕ ИДЕНТИФИКАТОРЫ
- **Проблема**: Принятие `id_map_info_ptr` за сам ID.
- **Инсайт**: Значение `id_map_info_ptr` — это **навигатор (offset/key)**, а не целевой ID приспособления. Поиск самого значения на диске бесполезен.

### 3. ОШИБКА ВЫХОДА ЗА ПРЕДЕЛЫ (Out of Bounds)
- **Проблема**: Интерпретация 16-битного указателя как 32-битного (uint32).
- **Симптом**: `Target address is out of bounds (file size: 0x...)`.
- **Решение**: Всегда проверяй, является ли указатель относительным (relative) или абсолютным. В Creo `id_map_info_ptr` — это **relative uint16**.

### 4. НАВИГАТОР (Navigator Insight)
- **Инсайт**: `id_map_info_ptr` — это **16-битное относительное смещение** (uint16) от начала блока `setup_data`.
- **Формула**: `Table_Start = setup_data_offset + (ptr_value & 0xFFFF)`.

### 5. ЛОЖНЫЕ ТИПЫ (False Positives)
- **Проблема**: Принятие файлов с суффиксами `_z` или `_o` за истинную сущность без проверки бинарных признаков.
- **Инсайт**: Имена могут быть ошибочными. 
    - Для **Заготовок** ищи `NeuPrtSld -> Base_Part` в `LargeText`.
    - Для **Отливок** ищи `PTC_SHRINKAGE_FACTOR` (8-byte double) в `BasFullData`.
- **Решение**: Всегда сопоставляй имя с найденным бинарным маркером (Validation by Evidence).

### 6. СЛОЖНЫЕ ИЕРАРХИИ (Implicit Hierarchies)
- **Проблема**: Ожидание, что один файл = одна сущность.
- **Инсайт**: Один бинарный контейнер может содержать несколько уровней (например, Мастер-модель содержит в себе и геометрию детали, и параметры уклонов, и является источником для сборки).
- **Решение**: Анализируй не только "что это за файл", а "какие связи он содержит".

### 7. 🔴 ДУБЛИ СВЯЗЕЙ: ИМЯ ≠ ОДИН ФАЙЛ (V104, 24.10.2026)

- **Симптом (владелец):** в связях одна модель идёт подряд десятками строк:
  `HB72501-401`, `HB72501-401`, `HB72501-401`… и то же в обратную сторону.
- **Причина:** **одно имя модели живёт во МНОГИХ путях** — `HB72501-401` = **98 файлов** в разных
  папках. Прежняя логика «каждый путь = отдельный узел, на каждую пару путей — своё ребро» давала
  **взрыв**: 30 строк `links` × 98 путей = **948 рёбер** на одну модель.
- **Проверка числами:** `SELECT model, COUNT(*) FROM snapshots WHERE model='HB72501-401' GROUP BY model` → 98.
- **Решение (в `plm_graph.py` и `plm_toolwin._graph_data`):**
  1. **Склейка по ИМЕНИ** модели — одна связь «имя → имя» = **одна строка**;
  2. **`SUM(qty)` в SQL** (`GROUP BY parent,child`) — количество суммируется, показывается `×N`;
  3. в карточке/на линии — **одна запись на модель-соседа** (ключ = имя, не путь);
  4. **вниз и вверх — РАЗНЫЕ списки** (состав vs входимость): одно имя в обоих — это разный смысл,
     а НЕ дубль.
- **Урок:** прежде чем строить граф по именам — проверь, сколько путей у имени. Если много —
  агрегируй **по имени**, а путь оставляй как «представитель» для ссылки.

### 8. 🔴 ТИП МОДЕЛИ: НЕ ПО ЧТЕНИЮ ФАЙЛА, А ПО РАСШИРЕНИЮ (V104)

- **Симптом (владелец):** `AX57K-V2` показан как **PRT**, хотя это **сборка** (`.asm`).
- **Причина:** тип брался из прочитанного файла (заголовок `#UGC:2 ASSEMBLY`) — но файл читается
  ТОЛЬКО при сборе превью; при исчерпанном бюджете (25000) или недоступности файла тип оставался
  `"?"`, а страница показывала PRT как «по умолчанию».
- **Решение:** тип определять **по расширению пути из базы** (`.asm.` → ASSEMBLY, `.prt.` → PART,
  `.drw.` → DRAWING) — без чтения файла; заголовок уточняет (ASSEMBLY/ASSEM_MFG), когда файл прочитан.
- **Урок:** визуальный признак (тип) не должен зависеть от того, «повезло ли» прочитать файл.

### 9. 🔴 ФИЛЬТР И СПИСОК: SQL, А НЕ PYTHON (V103, 24.10.2026)

- **Симптом (владелец):** «фильтр долго думает»; окно появляется не сразу.
- **Причина:** фильтр читал **ВСЮ таблицу `snapshots` в Python** (47k строк) на КАЖДОЕ нажатие;
  окно строилось ДО `mainloop` (обход диска 1.5–2.3 с); HTML-страница собиралась целиком в главном потоке.
- **Решение:** фильтр и `LIMIT` — **в SQL** (`WHERE ... LIKE ... LIMIT`, 0.05 с на 184 МБ);
  окно показывается сразу, данные догружаются (`root.after` + поток); HTML — порциями
  (`CREO_GRAPH_data.js`, `window.PLM_CHUNKS`), связи дорисовываются «живьём».
- **Урок:** «тормозит интерфейс» ≠ «медленный инструмент». Замерять каждый слой (БД / Python / Tk)
  ДО оптимизации: узким местом оказались чтение всей таблицы и работа до `mainloop`.



### 10. 🔴 ОДНОИМЁННЫЕ ПУТИ ≠ РАЗНЫЕ УЗЛЫ (V105, 24.10.2026)

- **Симптом:** модель не находится на странице/в графе, «не выводит ни картинку, ни чертёж»
  (`DF-STP2-VDF`, `170META-2-МОДЕЛЬ-ВЕРХА`).
- **Причина (три слоя):**
  1. **Один узел на КАЖДЫЙ путь** → у имени 7–98 узлов; превью лежит на ОДНОМ из путей и могло
     не попасть в выборку;
  2. **Первая порция и файл порций сортировались ПО-РАЗНОМУ** → часть моделей не попадала НИКУДА;
  3. **Лимит узлов страницы (12 000)** при 21 868 моделях со связями → 10 000 моделей невидимы.
- **Решение:** один узел на **ИМЯ** (путь-представитель — тот, где есть превью); единый порядок
  порций (`_ordered_keys`); лимит страницы поднят до 60 000 (ленивые порции держат скорость).
- **Урок:** если «модель не находится» — сначала проверить, **сколько путей у имени** и **влезает ли
  она в лимит страницы**; потом искать ошибку в фильтре.

### 11. 🔴 ФИЛЬТР: ИМЯ КОЛОНКИ ≠ SQL-ВЫРАЖЕНИЕ (V105)

- **Симптом:** на вкладке «Дерево» фильтр молчит — «что ни впиши, ничего не выводит».
- **Причина:** `_like_cond(words, ("model","designation",…))` — функция ждала **готовые
  выражения** (`"path LIKE ?"`), а получала **имена колонок** → SQL `(model OR designation …)`
  → исключение → `return []`.
- **Решение:** `_like_cond` принимает И имена колонок, И выражения (нормализует сама).
- **Урок:** меняя сигнатуру функции, **пройти всех её вызывающих** (`Select-String '_like_cond('`);
  исключения, проглоченные `except: return []`, выглядят как «пусто», а не как ошибка.

### 12. 🔴 НАСТРОЙКИ ГРАФА — В ОКНЕ, А НЕ В КОДЕ (V105)

- **Симптом владельца:** «настройки должны быть в НАСТРОЙКИ, а не зашиты в код; в HTML не понятно,
  где настройки и откуда читает».
- **Причина:** 13 ключей `graph_*` жили в `settings.json`, но **UI для них не было** — правились
  только руками в файле.
- **Решение:** раздел **«ГРАФ И HTML-КОНСОЛЬ»** в окне «Пути, исключения…» (12 числовых полей +
  превью + браузер + режим картинок); HTML-страница внизу пишет, **откуда взяты её значения**
  (файл `settings\settings.json`).
- **Урок:** ключ в `settings.json` без поля в окне = «зашито в код» с точки зрения владельца.


### 13. 🔴 БИТЫЙ DOUBLE = «ОБЪЁМ» ИЗ СОТЕН ЦИФР (V106, 24.10.2026)

- **Симптом (владелец):** в таблице в столбце «Объём» — простыня цифр на ~400 знаков
  (`1374822242512246569...0274176`), и она **копируется** в соседние столбцы.
- **Причина:** случайные 8 байт попали на шаблон `e0 02 <volume> 00 ed` → `struct.unpack` дал
  `1.3748222425122466e+290`. Таких записей в базе **3 570**.
- **Последствия (двойной вред):** (1) мусор в столбце; (2) фильтр `CAST(volume AS TEXT) LIKE '%170%'`
  ловил цифры → «выводит совсем не по фильтру» (3 959 попаданий вместо 663).
- **Решение:** `real()` проверяет правдоподобие (`_sane_number`: 0…1e9 мм³, без NaN/inf/минуса);
  показ — через `_vol_text`/`_vol`; **числа в подстрочный поиск НЕ берём**.
- **Урок:** любой `struct.unpack` из «дикого» файла может дать мусор — **всегда** проверять
  диапазон; число, которое нельзя объяснить физически, — это ошибка разбора, а не данные.

### 14. 🔴 ФИЛЬТР В ФОНЕ: Tk НЕ ЛЮБИТ ДОЛГИХ ЗАПРОСОВ (V106)

- **Симптом:** «фильтр по базе прям вешает окно».
- **Решение:** поиск в **отдельном потоке** + вставка строк в главном (`root.after(0, ...)`) +
  счётчик `seq` (устаревший результат не рисуем) + статус «ищу по базе…».
- **Урок:** любой запрос дольше ~0.2 с — в поток; Tk-виджеты трогаем ТОЛЬКО из главного потока.

### 15. 🔴 МАРКЕРЫ ТИПА В ГРАФЕ (V106)

- **Симптом:** «не понять в графе деталь / сборка / мануфактуринг».
- **Решение:** у каждого узла — цветной бейдж с буквой: **Д** деталь · **С** сборка ·
  **М** мануфактуринг (`ASSEM_MFG`) · **Ч** чертёж, + легенда типов над легендой связей.
- **Урок:** граф без подписи типа читается как «все одинаковые»; тип — обязательная подпись узла.


### 17. 🔴 ПОТОЛОК ПРЕВЬЮ ОСТАВЛЯЕТ ФАЙЛЫ БЕЗ КАРТИНОК (V107, 24.10.2026)

- **Симптом (владелец):** у ряда `.asm` «вместо картинки 0» (7 моделей из списка), хотя превью в файлах ЕСТЬ.
- **Причина:** жёсткий лимит `graph_media_limit = 25000` при **47 107** путях в базе — кэш
  заполнялся первыми 25 000 по порядку пути, а «хвост» **никогда** не читался.
  Проверка: `cut_preview(raw)` давал `[(17954,'jpg')]`, а в `media_cache.json` путь **отсутствовал**.
- **Решение:** `0 = без предела` + **ДОКАЧКА** (сначала читаются пути, которых нет в кэше);
  кэш инкрементальный — повторный прогон дочитывает недостающее. 22 624 → **33 965** превью.
- **Урок:** любой «разумный потолок» на массовом сборе данных надо делать **докачиваемым**,
  иначе он превращается в тихую потерю данных. Проверять: файл ЕСТЬ + превью в нём ЕСТЬ + кэш ПУСТ.

### 18. 🔴 НАСТРОЙКИ: ОДИН РЕЕСТР — ДВА ИНТЕРФЕЙСА (V107)

- **Симптом владельца:** «настройки в коде — ошибка; не пойму, где настройки HTML-окна».
- **Решение:** реестр `SETTINGS_SPEC` (ключ, подпись, тип, границы, группа) — **один источник**;
  из него строятся и окно tkinter, и панель в HTML; кнопка **⚙ НАСТРОЙКИ** прямо в HTML-странице
  (применение в браузере + «Скачать settings.json» для переноса в файл).
- **Урок:** настройка, которую нельзя увидеть и изменить в интерфейсе, для владельца «зашита в код»,
  даже если лежит в `settings.json`. Реестр + генерация UI из него снимает расхождение.

### 19. 🔴 КРУГОВОЙ ИМПОРТ СЪЕЛ РЕЕСТР (V107)

- **Симптом:** панель настроек в HTML пустая (`spec: 0`), хотя реестр есть.
- **Причина:** `import plm_settings` внутри `plm_graph` при запуске `plm_graph.py` как скрипта →
  цикл `plm_reader ↔ plm_settings` → `ImportError` → тихо `spec = []`.
- **Решение:** сначала `import plm_reader` (разрыв цикла), потом `plm_settings`; ошибку печатать.
- **Урок:** импорт «в глубине» функции может падать только при СКРИПТОВОМ запуске — проверять оба
  режима (`python -m`/`import` и `python файл.py`).

### 20. 🔴 ИНДИКАТОР РАБОТЫ: ОКНО НЕ ДОЛЖНО «МОЛЧАТЬ» (V107)

- **Симптом:** «не хватает индикатора, показывающего процесс при обновлении/сканировании/графе».
- **Решение:** крутилка + полоса прогресса (`work_start` / `work_progress` / `work_stop`) в строке
  состояния; включены на скане, проверке базы, сборке графа и поиске по базе.
- **Урок:** если операция длится >1 с, владельцу нужен видимый признак работы; текст статуса без
  движения читается как «зависло».

### 21. 🔴 ГЕНЕРАТОР ЛИТЕРАЛОВ УБИЛ JS-СТРАНИЦУ (V108, 24.10.2026)

- **Симптом:** `CREO_GRAPH.html:208 Uncaught SyntaxError: Unexpected number` — страница не выводит
  НИЧЕГО, настройки не открываются.
- **Причина:** в новой панели настроек использовались **имена-литералы генератора**
  (`__LISTMAX__`, `__LINKSMAX__`, `__DEPTH__`, `__NODESMAX__`, `__CHILDMAX__`).
  `plm_graph.build_html` **подставляет в них ЧИСЛА** (800/120/4/400/60) → в собранном JS вышло
  `window.800 = ...` → **свойство с числовым именем** → падение ВСЕГО скрипта.
- **Решение:** лимиты в рантайм-объекте `window.PLM_LIMITS`, чтение через `LIM(name, baked)`;
  панель настроек меняет их на лету. В JS **никогда** не писать `__ИМЯ__` — это слоты подстановки.
- **Защита:** самопроверка перед выпуском страницы теперь ловит **три** класса ошибок:
  `X.<число>`, остатки `__ИМЯ__`, дисбаланс круглых/квадратных скобок — страница **не пишется**,
  пока JS не чист (проверено: проверка поймала этот баг до выпуска).
- **Урок:** если страница падает с `SyntaxError` — искать **подстановки генератора**; проверять
  собранный файл, а не шаблон. Regex-проверка баланса `{}` НЕ ловит `window.800` — нужна отдельная
  проверка на «свойство числом».


- **Симптом:** полоса «ПУСК» закрывала низ окна со строкой состояния — окно перетаскивали каждый раз.
- **Решение:** размер/позиция по экрану: `w=min(1520, sw-40)`, `h=min(900, sh-120)`,
  по центру, но на 40 px **выше** центра.
- **Урок:** жёсткое `geometry("1520x900")` ломается на мониторах ниже 1024 px.


## 22. Страница PDM-Консоли НЕ в git — на шаре остаётся СТАРОЙ (V109)

- **Симптом:** «ASM <имя> опять без картинки», хотя в базе превью ЕСТЬ. На D: картинок
  33 504, на шаре — 29 991 (старая сборка).
- **Причина:** `CREO_GRAPH.html` и `CREO_GRAPH_data.js` **собираются на месте** и лежат в
  `.gitignore` → в git НЕ идут. Обновление меняет код, но **страницу не пересобирает** →
  владелец смотрит старую страницу (без новых превью, без истории).
- **Решение (V109):** после успешного `sync_by_manifest` страница **пересобирается сама**
  (`plm_graph.main()` с `--no-open`, в фоне; сбой пересборки не ломает обновление).
  Плюс страница честно говорит при отсутствии файла картинки:
  «картинки нет — соберите страницу заново (PDM-Консоль)» (`onerror` у `<img>`).
- **Урок:** **не хранить в git — значит не обновлять**. Если артефакт генерируется, обновление
  обязано его **перегенерировать**, иначе «новый код + старые данные».

## 23. Одно имя = .asm И .drw: при склейке побеждал ЧЕРТЁЖ (V109)

- **Симптом:** «ASM 5-5_5-NIZ-... не выводит картинку», хотя файл сборки с превью на месте.
- **Причина:** в базе у имени есть **два пути** — `.asm` (ASSEMBLY) и `.drw` (DRAWING).
  Узел страницы = **один на имя**, и при равных связях представителем становился **чертёж**.
- **Решение:** приоритет типа при склейке: **сборка > деталь > чертёж**
  (`_KPRI = {"ASSEMBLY":0,"PART":1,"MFG":1,"DRAWING":2}`), после приоритета «есть превью».
- **Урок:** у модели бывает несколько **ролей одного имени**; порядок выбора представителя —
  отдельная настройка смысла, а не случайность сортировки.

## 24. `\uXXXX` в самопроверке: данные ≠ код (V109)

- **Симптом:** страница не выпускалась: «экранированные `\uXXXX` в JS: 180».
- **Причина:** проверка искала `\u00XX` во **всём** JS, а в данных это **штатный JSON-эскейп**
  управляющих символов из Creo-строк (`\x01`, `\x02` — «Губка \x01n\x02117,2»).
- **Решение:** (1) чистить управляющие символы при сборке истории (`ch >= " "`);
  (2) в самопроверке искать `\uXXXX` **только в коде** — строки JS предварительно вырезаются
  (в файле уже есть `code` — JS без строк и комментариев).
- **Урок:** проверка «по всему тексту» даёт ложные срабатывания на **данных**.
  Различать код и данные до проверки.

## 25. Читать узел страницы: ключи идут НЕ в том порядке (V109)

- **Урок:** вывод «в странице нет X» делать ТОЛЬКО после разбора **всего объекта узла**,
  а не окна в N символов. Иначе — ложная диагностика (я на ней потерял цикл).

## 26. История файла: дата правки ≠ дата записи в базу (V110)

- **Причина:** в `changes` колонка `ts` = момент работы скана; `who` = `author` из паспорта Creo.
- **Решение:** реальную дату брать из описания правки — `revdate: -→31.08.23 05:11`
  (`RE_REVDATE`), а сам `revdate` из «что» вырезать (он показан отдельно).
- **Урок:** в журнале два разных «когда» — **когда правили** и **когда заметили**. Не путать.

## 30. Мануфактуринг (ASSEM_MFG) терялся среди сборок (V111)

- **Симптом владельца:** «сборки ASM и сборки мануфактуринг нужно разделять — сейчас в окнах,
  графах и связях это всё сборка».
- **Причина двойная:**
  1. флаг MFG ставился **только при чтении файла** (`b"ASSEM_MFG" in raw[:400]`), а читаются
     не все (бюджет превью) → из **6 353** MFG в базе в страницу попадало лишь **264**;
  2. в окне PLM Reader колонка «Тип» была **вообще пустой** (`"Тип": ""` в `_row_dict`),
     а в дереве тип был «оснастка/изделие/деталь» — без разделения сборки и мануфактуринга.
- **Решение:** главный признак MFG — **роль из базы** (`role='MFG'`) + тип файла + имя/путь
  с `-MFG`. Введены `_kind_of` (окно) и `_win_kind` (дерево): **СБОРКА МФГ / СБОРКА / ДЕТАЛЬ /
  ЧЕРТЁЖ**. В HTML — `isMfg()` (один признак для графа/карточки/списка), бейдж **М** отдельно
  от **С**, метка **MFG** отдельно от **ASM**.
- **Итог:** 264 → **4 132** узла MFG в странице.
- **Урок:** если признак выводится **из чтения файла**, а чтение **ограничено бюджетом** —
  признак будет **частичным**. Для классификации брать **данные базы** (роль), а не чтение.

## 31. Колонка «Тип» пустая = «всё одинаковое» (V111)

## 32. Вариант отображения — это НАСТРОЙКА, а не правка кода (V111)

## 33. Граф: «горизонтально/вертикально» — это НАСТРОЙКА ОТОБРАЖЕНИЯ (V112)

- **Запрос владельца:** «не нашёл настройку, чтобы граф/связи строились не в горизонталь,

  (уровни = колонки слева-направо), `y += RH` внутри уровня.
- **Решение:** параметр `graph_graph_layout` в реестре — `row` (слева-направо, было) /
  `col` (уровни сверху-вниз, узлы уровня в ряд). Ширина и высота холста считаются под строй:
  `W/H` зависят от `GL`. Смена настройки вызывает `render()` — перерисовка сразу.
- **Урок:** различать **построение** (какие данные) и **отображение** (как разложены).
  Владелец просил второе. «Не нашёл настройку» = она была **зашита в код** — вынести в реестр.

## 34. Блоки карточки должны быть ОДИНАКОВЫ (V112)

## 35. Скан пишется в ЧЕРНОВИК — это ЗАЩИТА базы (подтверждено)

## 36. Настройка есть, но её НЕ НАЙТИ = настройки нет (V113)

## 39. `db_facts`: `one()` не годится для списков (V114)

## 40. Мусорный объём снова вылез — фильтр нужен В КАЖДОМ выводе (V114)

## 41. «Вертикальный строй не понравился» — улучшать, а не спорить (V115)

- **Отзыв владельца:** «вертикальная связь очень не очень» (всё остальное работает).
- **Что было не так:** в вертикальном строе узлы уровня шли **одной длинной строкой** без переноса
  (`x += CW` по всем узлам) → граф уходил **вправо за экран**, а уровни уползали вниз «простынёй».
- **Решение (не «убрать», а «сделать нормально»):**
  1. внутри уровня — **перенос строк сеткой**: `PER_ROW` по ширине окна, уровень занимает
     несколько рядов (`r = floor(i/PER_ROW)`), высота уровня `ceil(n/PER_ROW)*RH`;
  2. **горизонтальный строй оставлен по умолчанию** (`row`) — как и было;
  3. добавлена кнопка **«↔ Горизонтально (по умолчанию)»** — один клик возвращает привычный вид
     (сбрасывает строй графа **и** связей).
- **Урок:** «мне не нравится вариант» ≠ «уберите вариант». Сначала **понять, чем он плох**
  (здесь — раскладка без переноса), починить, и дать **быстрый возврат** к прежнему.
  Вариант по умолчанию менять не нужно — он и был `row`.

## 42. Настройку, изменённую в браузере, не видно в файле (V115)

- **Наблюдение:** в `settings.json` владельца настроек строя **нет**, а в браузере они были
  изменены. Причина: панель «⚙ НАСТРОЙКИ» пишет правки в **`localStorage`** (`plm_graph_cfg`),
  а не в файл — файл меняется только кнопкой **«💾 Скачать settings.json»**.
- **Следствие:** «сбросить» надо уметь **из браузера** — отсюда кнопки «↔ Горизонтально» и
  «↺ Сбросить всё» (обе чистят/правят `localStorage`).
- **Урок:** если настройка живёт в двух местах (файл + браузер), у пользователя должна быть
  **кнопка возврата** в каждом из них; иначе он «застрянет» в варианте, который сам же включил.

## 43. Настройка СТРОКОЙ из файла молча включала потолок превью (V116)

- **Симптом владельца:** «INSERT-STP-S1 нет опять фото», «вроде уже должно было решиться» —
  у ряда моделей нет картинки, хотя превью **в файлах ЕСТЬ** (проверено чтением: `[(24005,'jpg')]`).
- **Корень (найден по факту):** в `settings.json` лежало
  **`"graph_media_limit": "25000"` — СТРОКА** (старый формат сохранения).
  `_validate_settings` проверял **только 4 ключа** (`max_size_mb`, `show_limit`, `depth`,
  `purge_keep`), а настройки графа — **НЕТ** → `out.update(data)` клал строку как есть →
  `int("25000")` = 25000 → **жёсткий потолок 25 000 превью** включался молча.
  Итог: 8 494 модели без картинок, кэш обрезан **36 341 → 25 000**.
- **Решение:** нормализация **по всему реестру** `SETTINGS_SPEC` (int/bool/choice), плюс правило
  **устаревшее `25000` → `0` (без предела)**. Проверено: `graph_media_limit` стал `0` (int).
- **Урок:** `out.update(file_data)` **без проверки типов** — мина. Файл настроек может содержать
  строки, и тогда «умолчание в коде» **не работает**: значение из файла сильнее.
  Меняя умолчание в коде, **проверь, нет ли старого значения в файле у пользователя**.

## 44. Смена умолчания в коде ≠ смена у пользователя (V116)

- **Наблюдение:** в V107 предел превью подняли `25000 → 0`, но у владельца **осталось 25000**:
  файл настроек уже существовал и **перебивал** новое умолчание.
- **Правильный приём:** при **смене смысла** параметра — **миграция** (как для `25000 → 0`),
  а не только правка `DEFAULT_SETTINGS`.
- **Урок:** «я же поменял в коде» — не аргумент, если значение есть в `settings.json` или в
  `localStorage`. Нужна миграция или явная нормализация устаревших значений.

## 45. Вертикальный граф «обрезал окно» — размеры от РЕАЛЬНОЙ области, не от окна (V116)

- **Симптом:** «вертикально — обрезает окно».
- **Причина:** ширина/высота холста считалась от `window.innerWidth` и от **числа уровней**,
  а не от **фактической раскладки**; в вертикали низ графа не попадал в холст.
- **Решение:** (1) `PER_ROW` и ширина — от **ширины области графа** (`gbox.clientWidth`), холст
  не шире области (нет горизонтальной прокрутки); (2) высота — по **накопленному низу** раскладки
  (`colBottom`), а не `cols.length * RH`.
- **Урок:** размеры контейнера брать у **самого контейнера** (`clientWidth`), а не у окна:
  боковая панель/карточка «съедают» ширину, и расчёт от окна даёт обрез.

## 46. Раскладка должна быть РАЗБОРЧИВОЙ, а не только правильной (V117)

- **Отзыв владельца:** «вертикальные связи — **не очень красиво** строятся, можно по-интереснее».
- **Что было не так:** раскладка была **формально верной** (сетка с переносом, холст по окну),
  но **нечитаемой**: отступ между уровнями **4 px** при высоте узла 24 → уровни **сливались**;
  не было видно, где кончается один уровень и начинается другой — «куча».
- **Решение:** (1) у каждого уровня — **полоса-заголовок** «уровень N · узлов K» (подсветка слева
  + рамка); (2) отступ между уровнями **4 → 22**; (3) ряды внутри уровня **24 → 28**; (4) высота
  по фактическому низу. **Горизонталь не тронута.**
- **Урок:** «правильно» ≠ «понятно». Проверять **визуально** (скриншот/глазами), а не только
  «координаты не выходят за холст». Группировку (уровни) надо **показывать**, а не подразумевать.

## 47. Как «починить красиво», не сломав работающее (V117)

- **Приём:** менять **только ветку вертикального строя** (`if (GL === "col")`), а горизонтальную
  (`else`) не трогать вовсе; плюс отдельный массив `lvlBand`, который рисуется **только** в col.
- **Проверка:** после правки — `_check_page` + проверка, что `GL === "col"` встречается и в
  раскладке, и в отрисовке (иначе полосы не появятся или появятся в горизонтали).
- **Урок:** улучшая один режим, **изолируй** его код; иначе «сделал красиво вертикально —
  сломал горизонтально».

## 48. Вечный «НУЖЕН СКАН»: проверка ≠ скан (V118)

- **Симптом владельца:** «сканирую, закрываю окно — открываю, **опять** висит «НУЖЕН СКАН:
  новых 476 · изменённых 3 · пропало 584»».
- **Корень (вечный цикл):** проверка актуальности `do_check` шла **с другими правилами**, чем скан:
  не применялись `latest_only` («только последние версии») и `recurse`. Поэтому промежуточные
  версии (`*.prt.2`, `.3`, `.4` — их скан **сознательно не берёт**) считались «новыми» (476).
  Скан их не забирал → сообщение **возвращалось всегда**.
- **Решение:** `do_check` использует **те же правила**, что скан (`latest_only`, `recurse`,
  `max_size_mb`); **«пропало» не требует скана** (это устаревшие записи, скан их лишь уберёт).
  Было 476 → стало **2** (реально новые файлы).
- **Урок:** **проверка должна мерить ТЕМ ЖЕ эталоном, что и работа.** Если скан фильтрует версии,
  а проверка — нет, получится вечный цикл «нужен скан», который скан не лечит. Сравнивать правила
  скана и проверки — обязательный шаг.

## 49. Ложная тревога от фильтрации базы (V118)

- **Грабля по ходу:** сначала я отфильтровал `prev` (пути из базы) через `_filter_latest` — чтобы
  «пропало» не показывало старые версии. **Стало хуже:** у файла на диске может быть «старший»
  сосед **только в базе** (его уже нет на диске) → известный файл выглядел **«новым»** (33 ложных).
- **Правильно:** правила применять **только к файлам диска** (`files`), а `prev` брать **как есть** —
  именно так делает скан.
- **Урок:** фильтруя одну сторону сравнения, проверь, что **не сломал** другую. Здесь «оптимизация»
  «убрать старые версии из базы» дала **новые** ложные «новые» файлы.

## 50. «Не двигается» = контент умещается в окно (V118)

- **Отзыв владельца:** «река вроде как **застыла**, динамики не видно».
- **Корень:** ширина холста `W = max(ширина_окна, число_бинов × 26)`. При малом числе периодов всё
  **умещалось** → ни прокрутки, ни зума; плюс зум сбрасывался при `resize` (перерисовка).
- **Решение:** у каждого периода **гарантированная ширина** (месяц 46 px, неделя 64, день 34) →
  холст **шире окна** → есть что прокручивать и зумить.
- **Урок:** «не двигается» надо проверять **условием переполнения** (`bbox` vs размер окна), а не
  визуально. Если контент адаптивно влезает — прокрутки не будет **по определению**.

## 51. Подсказки/легенды — ВНЕ прокручиваемой области (V118)

- **Отзыв владельца:** «подсказки в окне прям **на карточках** и **двигаются вместе с окном**».
- **Корень:** легенда типов рисовалась `canvas.create_text(...)` **на холсте графа**, внутри
  `scrollregion` → накладывалась на узлы и уезжала при прокрутке.
- **Решение:** легенда перенесена в **подпись-лейбл над картой** (`grs.config(text=...)`).
- **Урок:** всё «постоянное» (легенды, подписи, заголовки) — **в фиксированной рамке**, а не на
  прокручиваемом холсте. На холсте — только сам контент.

## 52. Бейдж и слово рядом должны означать ОДНО (V119)

- **Отзыв владельца (скриншот):** «Куда входит: бейдж **С** (сборка) — правильно, а написано
  **«деталь»**».
- **Корень:** в списках «Состав / Куда входит» рядом с бейджем выводился `x[1]` — это **вид связи
  из базы** (`деталь`/`копия`/`заготовка`), а **не тип модели**. Бейдж показывал тип (С),
  а слово — вид связи («деталь») → **противоречие на одной строке**.
- **Решение:** слово берём из **типа модели** (`kindWord`), чтобы **совпадало с бейджем**;
  вид связи показываем **только** для содержательных случаев — **«копия»** и **«заготовка»**.
- **Урок:** если рядом стоят **два индикатора одного объекта**, они должны читаться **согласованно**.
  «Бейдж по типу, слово по связи» — источник путаницы. Слова-метки брать из **того же поля**, что бейдж.

## 53. Два разных «типа» в одной базе: тип модели vs вид связи (V119)

- **Факт:** в базе есть (1) **тип модели** (`role`/расширение: деталь/сборка/мануфактуринг/чертёж)
  и (2) **вид связи** (`links.type`: «деталь»/«копия»/«заготовка»). Оба содержат слово «деталь» —
  именно это и сбивает.
- **Урок:** различать **свойство объекта** и **свойство связи** между объектами. В интерфейсе
  свойство объекта — у имени (бейдж + слово), свойство связи — отдельной пометкой (×N, «копия»).

## 54. «Не выводит HTML» = отбор узлов, а не скан (V120)

## 55. Производность и состав — РАЗНЫЕ вещи (V121)

- **Отзыв владельца:** «`DIN912` — исполнения входят в кучи сборок, но ПДМридер нигде это не указывает»

  **отбрасывать**, а не «вырождать» на исходный ключ.
- **Урок:** «одна карточка — одни связи» ≠ правда. **Разделяй свойство объекта и свойство связи**,
  а производность показывай **своим блоком**, иначе 44% рёбер на карточке окажутся чужими.

## 67. Занятый файл SQLite даёт ПУСТОЙ список таблиц БЕЗ ОШИБКИ (V127)

## 70. ДВОЙНОЙ цикл по путям = ×4 размножение связей (V128)

- **Грабля:** в `collect_by_path` рёбра строились **двойным циклом по путям имён**:
  ```python
  for pk in by_name[имя-источника]:      # у имени до 4 путей
      for ck in by_name[имя-приёмника]:  # × до 4 путей
          edges.append(...)              # ОДНА связь → 16 рёбер
  ```

- **Как правильно:** **СВЯЗЬ = ПАРА ИМЁН = ОДНО ребро**; путь — только чтобы выбрать

  есть размножение; и `len(edges)` должен совпадать с числом пар в `links`+`derived`.
- **Урок:** свёртка «имя → много путей» НЕ должна размножать СВЯЗИ. Размножай **узлы**, а **связи — нет**.

## 71. 🔴 `INSERT INTO t VALUES(...)` БЕЗ СПИСКА КОЛОНОК — падает на ЧУЖОЙ базе (V133)

- **Лечение:** **ВСЕГДА** писать список колонок: `INSERT INTO t (c1,c2,...) VALUES (...)`.
  Работает и на базе с чужой колонкой, и без неё; чужие данные **не затираются**.
- **Проверка:** `PRAGMA table_info(<таблица>)` против `SCHEMA` в коде — искать ЛИШНИЕ колонки.
- **Урок:** база может быть **изменена другим инструментом**. Код обязан пережить **лишнюю колонку**.

## 83. 🔴 `CREATE TABLE` ВНУТРИ `try/except` — таблицы НЕТ, исключение ПРОГЛОЧЕНО (V135)

- **Факт:** боевая база отвечала `no such table: health`; «здоровье файлов Creo» не выводилось нигде.
- **Причина:** `con.execute("CREATE TABLE IF NOT EXISTS health …")` стоял **внутри `try`, рядом с
  `INSERT`**, а `except Exception: pass` **гасил** любую ошибку. Ошибка была — значит и `CREATE`,
  и `INSERT` молча не выполнялись: **пустой `except` съел диагноз**, и ни в логе, ни в окне ничего
  не появилось.
- **Лечение (V135, коммит `5083292`):** `CREATE TABLE health` вынесен в **`SCHEMA`** (выполняется
  один раз в `connect()` через `executescript`), в `try` остался **только `INSERT`**.
- **Правило:** **структура БД создаётся в ОДНОМ месте — `SCHEMA`. `CREATE` в рабочем цикле +
  пустой `except` = «таблицы нет, и никто не знает почему».** Проверка: `SELECT name FROM
  sqlite_master WHERE type='table'` в СВЕЖЕЙ базе — таблица обязана быть.
- **Общее правило дома:** **пустой `except: pass` рядом с работой с данными — запрещён.** Он
  превращает «ошибка» в «данных нет», и это две разные новости для владельца.

## 88. 🔴 СКРИПТ ОБНУЛИЛ ФАЙЛ: `open(...,"wb")` ДО ФОРМИРОВАНИЯ СОДЕРЖИМОГО (28.10.2026)

**Симптом:** `plm_reader.py` стал **0 байт** — файл уничтожен, а инструмент перестал компилироваться.

**Причина:** одна строка кода:
```python
open(p, "wb").write(nl.join(out))     # ← СМЕРТЕЛЬНО
```
`open(p,"wb")` **обнуляет файл СРАЗУ при открытии**. Затем `nl.join(out)` бросил `TypeError`
(в `out` смешались `bytes` и `str`) — и запись не состоялась, а **файл уже был пуст**.

**Лечение:** `git checkout -- <файл>` — файл в репозитории, потеря нулевая. Опасный скрипт удалён.
Правка сделана коротким якорем `editor`.

**ЗАКОН (грабля):**
> **НИКОГДА не открывать файл на запись, пока содержимое не СОБРАНО ПОЛНОСТЬЮ в память.**
> ```python
> # ❌ ТАК НЕЛЬЗЯ
> open(p, "wb").write(build())          # build() может бросить → файл пуст
> # ✅ ТАК НАДО
> data = build()                         # сначала всё посчитали
> tmp = p + ".tmp"
> open(tmp, "wb").write(data)            # пишем во временный
> os.replace(tmp, p)                     # атомарная подмена
> ```
> Тот же приём уже применён в доме: `plm_settings.save_settings_file` (tmp → `os.replace`),
> `engine._publish`. **Бери готовый образец, не пиши «в лоб».**

**Дополнительно (смешение типов):** в одном скрипте **не смешивать `bytes` и `str`**.
Если файл читается как байты (`"rb"`) — весь конвейер держать в байтах, и наоборот.
`TypeError: expected a bytes-like object, str found` — признак этого.

**Проверка приёмки после ЛЮБОГО скрипт-писателя:** размер файла > 0 **и** `py_compile` **и**
`git diff --numstat` (честный, не «весь файл»).

## 91. 🔴 КОДИРОВКИ В ФАЙЛАХ CREO МЕНЯЮТСЯ ОТ ВЕРСИИ К ВЕРСИИ (наблюдение владельца)

## 92. ⚠️ ПРОВЕРКА EOL «В ЛОБ» ДАЁТ ЛОЖНУЮ ТРЕВОГУ ПРИ `core.autocrlf=true` (28.10.2026)

**Симптом:** замер показывает «было LF → стало CRLF» / «🔴 СМЕНА EOL» — а на деле всё цело.

**Причина:** в доме `git config core.autocrlf = true`. Тогда:
- **в репозитории (blob) — ВСЕГДА LF**;
- **в рабочей копии — CRLF** (git конвертирует при checkout);
- сравнение **рабочего файла с `git show HEAD:файл`** даёт «разные EOL» **всегда** — это **не порча**.

**Как проверять ПРАВИЛЬНО (по грабле §16):**
1. **Главный признак порчи — `git diff --numstat`**: если правка 4 строки, а показывает
   **весь файл** (`403 403`) — **это регресс EOL**;
2. если `--numstat` честный (`19 0`, `30 1`) — **EOL в порядке**, что бы ни показывал счётчик CR;
3. **не сравнивать** рабочий файл с blob напрямую при `autocrlf=true`;
4. предупреждение `LF will be replaced by CRLF the next time Git touches it` — **норма**,
   а не ошибка.

**Живой случай 28.10.2026:** трижды объявлял «EOL испорчен» по счётчику, трижды тревога была
**ложной**; и наоборот — **настоящий** регресс (§16, `403/403`) был виден сразу в `--numstat`.

## 94. 🔴 ПРИЧИНА «НАСТРОЙКА НЕ СОХРАНЯЕТСЯ» — В ОКНЕ ДВА ПОЛЯ ОДНОГО КЛЮЧА (28.10.2026, V138)

**Симптом (эстафета V137, БАГ A):** в `settings.json` ключа `config_pro` **нет**, владелец вписывал

**Как искали (и как надо искать):** НЕ глазами по коду, а **пробой**, которая вызывает `save()`
на **ВРЕМЕННОМ** файле настроек и печатает, что уходит на запись:

```python

plm_paths_window.save_settings_file = plm_settings.save_settings_file   # окно берёт имя ИМПОРТОМ

```
**Живые факты пробы (по шагам, каждая строка — диагноз):**
1. `PathsWindow(root, on_save=None)` → `TypeError: missing 4 required positional arguments` —
   сигнатура: `(parent, settings, tk, ttk, filedialog, on_save=None)`;
2. после первой правки → `KeyError: 'template_folders'` — **окно падало на ОТКРЫТИИ**: строка
   осталась в `__init__`, а ключа в `self.rows` уже нет (наследие удаления блока «ШАБЛОНЫ»);
3. `save()` → `NameError: name '_ps' is not defined` — `import plm_settings as _ps` был **локальным
   в `__init__`**, а `save()` его не видит. Лечение: `self.spec = list(_ps.SETTINGS_SPEC)` в `__init__`;
4. `save()` прошёл, но во времянке `config_pro = ''` — **самое важное**: `config_pro` лежит в
   **едином реестре** `SETTINGS_SPEC` (тип `text`), и цикл «все настройки из реестра» брал его из поля
   раздела ПАРАМЕТРЫ (всегда пустого) и **затирал реальный путь из `e_cfgpro` пустой строкой**.

**ПРИЧИНА (корень):** **два поля на один ключ**. Раздел «CONFIG.PRO» пишет `e_cfgpro`, а раздел
«ПАРАМЕТРЫ» (автосборка из реестра) — своё поле того же ключа; кто последний, тот и прав.

**ЛЕЧЕНИЕ:** поле-хозяин пишется **ПОСЛЕ** цикла реестра:
```python
_cp = self.e_cfgpro.get().strip().replace("/", "\\")
...
# цикл по gbools/gchoice/gvars из SETTINGS_SPEC
self.settings["config_pro"] = _cp        # 🔴 ПОСЛЕ цикла — хозяин главнее
save_settings_file(self.settings)
```
**Правило дома:** если ключ есть и в отдельном поле, и в автосборке из реестра — **сначала цикл,
потом хозяин**. Иначе настройка «исчезает» без ошибки.

**Второе правило (тип `list`):** ветка `else` рисует **числовую** крутилку; тип `list` надо ловить
явно (`elif typ == "list"` → `Entry` + разбор `split_list`), иначе ввод вроде `4орлорпро` падает
в `int(float(...))` → `except: pass` → **ключ теряется молча** (грабля 83).

**Замер приёмки этой ноги:** `COMPILE OK` · `SMOKE OK` · проба B/C: `ШАБЛОНЫ в папках сканирования:
False` (и до, и после повторного открытия), `param_pick = ['НАИМЕНОВАНИЕ','ОБОЗНАЧЕНИЕ']` в файле.
Пробы писали в `%TEMP%` — живые настройки НЕ тронуты (грабля 18).

> **«ГЛАВНОЕ: либо одно править, либо другое!»** (владелец)

| Нога | Читает | Пишет | Правим, если неверно |

### 100. ЗАМЕР ХЕША — ТОЛЬКО НОРМАЛИЗОВАННЫМ ХЕШЕРОМ (ложная авария 28.10.2026)

**Что случилось.** Владелец заявил: «опять непроверенные данные отправляются в GitHub».
Я «подтвердил» фактом: **12 из 22 файлов** поставки расходятся с `version.json`. Проверял так:

```powershell
Get-FileHash $file -Algorithm SHA256     # ❌ НЕВЕРНЫЙ ЗАМЕР
```

**Почему это ложь.** Рабочий диск на Windows хранит текст с **CRLF**, git-blob — с **LF**.
Хешеры дома **нормализуют переводы строк** перед счётом:

| Кто | Строка | Код |
|---|---|---|
`make_version_json.sha256` | 31–35 | `data = f.read().replace(b"\r\n", b"\n")` |
`engine._sha256_file` | 3416–3421 | `data = f.read().replace(b"\r\n", b"\n")` |

**`Get-FileHash` нормализации НЕ делает** → у CRLF-файлов он **никогда** не совпадёт с манифестом.
Живой замер, доказывающий причину:

```
disk plm_reader.py : 15936 Б, CRLF=494, sha=7297D2C1…
git  plm_reader.py : 15442 Б, CRLF=0,   sha=266DC685…
разница 494 Б  ==  РОВНО число CRLF
```

**Вывод (правило).**

- **100.1.** Сверять хеш можно **только тем хешером, что пишет манифест**:
  `python -c` запрещён → пробой-файлом: `import make_version_json; make_version_json.sha256(path)`.
- **100.2.** `Get-FileHash` и `certutil` для сверки поставки **ЗАПРЕЩЕНЫ** — они дают **ложную аварию**.
- **100.3.** Прежде чем объявить «расхождение» — **докажи метод замера**: посчитай размер и число CRLF
  с обеих сторон. Разница в байтах, равная числу CRLF, = **это EOL, а не рассогласование**.
- **100.4.** Проверка **с обеих сторон**: диск ↔ git-объект (`git show HEAD:path`) ↔ `version.json`
  (`sha256()`). Только совпадение **всех трёх** = поставка цела.
- **100.5.** `raw.githubusercontent.com` **кэшируется** (минуты). Старый текст в raw — **не авария**:
  истина — **git-объект коммита** (`git show <sha>:<path>`), а не HTTP-ответ.
- **100.6.** «Проверка прошла» ≠ «данные верны», если **инструмент замера не тот** (§99.3.1).

**Цена.** Ложная тревога: владелец получил обвинение в свой адрес, время потрачено, доверие к отчётам
упало. Причина — **мой замер, а не поставка**. Настоящее состояние: **поставка цела**, все 22 хеша
совпадают нормализованно, `CODE_FILES` = набор манифеста.

## 113. 🔴 `editor` НЕ СОХРАНЯЕТ EOL — ПРАВИТЬ ФАЙЛЫ ДОМА ТОЛЬКО СКРИПТОМ (29.10.2026)

**Что было (дважды за одну ногу):**

2. «Исправил» `SKILL_creo_index.md` на CRLF — а файл был **LF** (`CR=0 LF=94`) ⇒ **создал** регресс,
   которого не было: `git diff` показал `106 / 94` вместо `+12 / −0`.

**Оба раза лечилось:** `git checkout -- <файл>` + правка **скриптом Python** с сохранением EOL:
```python
raw = open(P, "rb").read()
bom = raw[:3] == b"\xef\xbb\xbf"
EOL = b"\r\n" if raw.count(b"\r") else b"\n"          # СОХРАНИТЬ как было
sep = "\r\n" if EOL == b"\r\n" else "\n"
lines = raw.decode("utf-8-sig" if bom else "utf-8").split(sep)
# ... правка lines ...
out = sep.join(lines).encode("utf-8")
if bom: out = b"\xef\xbb\xbf" + out                    # BOM сохранить
open(P, "wb").write(out)
```

**ПРАВИЛО (жёсткое):**
1. **Перед правкой файла дома — ЗАМЕР EOL:**
   `$b=[IO.File]::ReadAllBytes($p); "$($b|?{$_ -eq 13}).Count / $($b|?{$_ -eq 10}).Count"`
2. **Правка — скриптом, НЕ `editor`** (для файлов, которые ведёт git дома).
3. **Проверка после:** `git diff --numstat` должен показать **число реально добавленных строк**.
   Показал «весь файл» ⇒ **EOL поехал** ⇒ `git checkout`, переделать.
4. **«Исправление EOL» без замера — ЗАПРЕЩЕНО**: можно создать регресс там, где его не было.

**Связь:** `SKILL_edit_gotchas.md` §16 — регресс EOL уносит **весь файл** в коммит.

(`0x4080`, `0x4800`, `0x5000`), и **сразу записал «уточнить фильтр до `id < 0x4000`»**.

```
_mill_turn.asm.1:  Creo = 53
    фильтр id < 0x4000 -> 50   ❌ ПОТЕРЯНО 3 элемента
```

**⇒ «Красивые» id (степени двойки) оказались ЛЕГАЛЬНЫМИ `feat_id`.** Догадка стоила бы 3 элементов.

**ПРАВИЛО:**
1. **Число, похожее на маркер/магию — НЕ признак.** Признак берётся **из замера по эталону**.
2. **Менять фильтр только по счёту против эталона** (Creo/J-Link), и **сравнить счёт ДО и ПОСЛЕ**.
3. **Правило-отмену фиксировать явно** («ОТМЕНА ПРЕДЫДУЩЕЙ ПРАВКИ»), чтобы следующая нога
   не вернулась к ложной правке.

## 116. 🔴 «СЕКЦИЯ» МОЖЕТ БЫТЬ ПОЛЕМ: `names_table` — ВНУТРИ `MdlStatus` (29.10.2026)

**Что было:** половину сессии я читал «секцию `names_table`» — искал байтовую строку `names_table`
и брал **400 000 байт после неё**.

**Что показал замер TOC:**
```
MdlStatus    offset=0x000377F0  len=32638
names_table  НЕТ в TOC                    ← строка names_table — ИМЯ ПОЛЯ СХЕМЫ, не секция!
```
**⇒ «Секция» `names_table` = **та же** `MdlStatus`, которую читает `feat_records.py`** — читали
**одни байты двумя способами**, не зная об этом.

**ПРАВИЛО:**
1. **Имя области проверяй по TOC (`#UGC_TOC`), а не по вхождению строки.** Есть в TOC — это секция;
   нет — это **поле/ключ схемы внутри секции**.
2. **Перед чтением своей «секции» — загляни, нет ли уже инструмента дома по этой секции**
   (`feat_records.py` читал `MdlStatus` **до меня**).
3. **Две разные дороги к одним байтам = сигнал, что модель неверна.**

## 117. 🔴 ИНСТРУМЕНТ ДОМА МОЖЕТ БЫТЬ ПОД ДРУГУЮ ВЕРСИЮ Creo (29.10.2026)

```
в MdlStatus файла:   'featssrf'=0 · 'cutextrude'=0 · 'feathole'=0 · 'group'=0 · 'is_header'=0
```

## 118. 🔴 `\xe3` В ТЕКСТЕ = ЛОЖНАЯ ВЕДУЩАЯ ЦИФРА `3` (29.10.2026)

**Что было:** в «сыром» чтении байтов `\xe3` попадает в строку как символ `'3'`:
```
видно:  '3M16x1.5'  '3M8x1.25'  '3PRO_MP_CSYS'  '3GEOMETRY'  '3ISO'  '3H'
на деле: 'M16x1.5'   'M8x1.25'   'PRO_MP_CSYS'   'GEOMETRY'   'ISO'   'H'
```
**⇒ несколько РЕАЛЬНЫХ имён `.prt` (резьбы `M16x1.5`, `M8x1.25`; системы координат `PRO_MP_CSYS`,
`PRO_MP_ALT_CSYS`; `GEOMETRY`, `ISO`) я не видел, потому что читал их с мусорной ведущей цифрой.**

**ПРАВИЛО:** если имя начинается с цифры, **похожей на остаток маркера** (`3`, `2`, `5`) —
**отдели её и проверь обе версии против Creo.** **Не считать «имя начинается с 3» именем.**

## 119. 🔴 РАСШИФРОВКУ СОКРАЩЕНИЯ БЕРУ У ВЛАДЕЛЬЦА, НЕ ВЫДУМЫВАЮ ПО БУКВЕ (29.10.2026)

**Что было:** `A_1..A_10` я расшифровал как «**A**xis = ОСЬ» — и записал в скилл как вывод.
**Владелец:** «`ADTM1...3` — **плоскости**» ⇒ **`A` в `ADTM` = Auxiliary (вспомогательная), НЕ Axis.**

**ПРАВИЛО:**
1. **Сокращения Creo — это ЯЗЫК, а не загадка.** Расшифровку беру у владельца / Creo / документации PTC.
2. **Не выдумывать по первой букве.** `A` может быть `Axis`, `Auxiliary`, `Assembly`, `Alt`…
3. **Сомневаешься — спроси владельца** (он знает номенклатуру; ошибка в термине дороже вопроса).
4. **Словарь пополнять замером + подсказками владельца** (см. карту файла в
   `READ\SKILL_creo_tree_jlink_etalon.md`: `ADTM`=плоскость, `NC`=производство, `ASM`=сборка,
   `DEF`=по умолчанию, `CSYS`=СК, `PRO_MP_*`=массовые свойства, `TRF`=матрица 4×4, `COG`=центр масс).

## 120. 🔴 ГРАНИЦУ БЛОКА БЕРИ ЗАМЕРОМ, А НЕ ПО ДОКУМЕНТАЦИИ (29.10.2026)

**Что было:** писал границу TOC как `#UGC_TOC … #END_OF_TOC` (так в документации).
**Замер:** `#END_OF_TOC` в файлах Электона — **0 вхождений**; реальная граница — **`NEXT_TOC_ENTRY`**.
**Плюс:** `#UGC_TOC` встречается **3 раза** ⇒ брать **первый**.

**ПРАВИЛО:**
1. **Каждый маркер-границу ПРОВЕРЯЙ счётчиком** в конкретном файле (`.count()`), а не по памяти/докам.
2. **Повторяющийся маркер** (`#UGC_TOC` ×3) — **уточни, какой брать** (первый), и запиши это.
3. **«По документации» ≠ «в этом файле»** — версия Creo меняет границы.

## 121. 🔴🔴 СОВПАЛО НА 2–3 ПРИМЕРАХ — ЭТО НЕ ПРАВИЛО. ПРОВЕРЯЙ НА ВСЕХ (29.10.2026)

**Что было (самая дорогая ошибка этой ноги):** нашёл поле `obj_type` в таблице `item_names`,
увидел **3 совпадения** с моим `b`:
```
A_1 → obj_type=21 (мой b=21) ✅    RIGHT → 5 (b=5) ✅    PRT_CSYS_DEF → 25 (b=25) ✅
```
**и СРАЗУ записал в скилл: «`b` = `obj_type` — ЕДИНЫЙ СЛОВАРЬ ВИДОВ».**

**Что показал замер по 323 файлам:**
```
obj_type = 94   →  ADTM25 (ПЛОСКОСТЬ) и MILL01 (СТАНОК)     ← ОДИН код, РАЗНЫЕ виды
obj_type = 124  →  MILL01 (СТАНОК) и SVERLO-50 (СВЕРЛО)
obj_type = 66   →  APNT0..6, PNT0..5 — но 88 ВХОЖДЕНИЙ при 12 именах
имя ADTM* → 15+ РАЗНЫХ кодов: 5, 50, 59, 106, 108, 176, 216, 219, 227, 253 …
```
**⇒ «единый словарь» РАССЫПАЛСЯ. Правку пришлось ОТОЗВАТЬ (написав «ОТМЕНА»).**

**ПРАВИЛО:**
1. **Совпадение на 2–3 наблюдениях — ГИПОТЕЗА, а не вывод.** Прежде чем писать в скилл —
   **проверь на ВСЕХ доступных файлах** (у нас их 323 — прогон занимает минуту).
2. **Критерий записи:** **счёт по всему массиву**, а не «выглядит логично».
   (`_mill_turn` 53 = 53 — критерий ✅; «3 совпало» — не критерий ❌.)
3. **Ошибочный вывод В СКИЛЛЕ дороже ошибки в чате**: следующая нога **поверит** и не перепроверит.
   **Поэтому отмену пиши явно** («ОТМЕНА ПРЕДЫДУЩЕЙ ПРАВКИ») со списком опровергающих фактов.
4. **Число наблюдений указывай явно:** «проверено на 323 файлах» vs «совпало 3 раза» —
   **это РАЗНЫЕ уровни доказательности**, и в скилле должно быть видно, какой.
5. **Не путать таблицы:** в файле ДВЕ разные `item_names` (список датумов и записи изменений) —
   **номера из одной НЕ переносятся в другую.**
