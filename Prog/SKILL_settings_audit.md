# АУДИТ НАСТРОЕК ДОМА: КАК ПРОВЕРЯТЬ ЧЕСТНО

## 1. ГЛАВНОЕ ПРАВИЛО: ПОИСК ПО ИМЕНИ В ТЕКСТЕ ВРЁТ

Проверка «настройка упоминается в файле ⇒ она работает» **неверна**. Доказано на доме
(04.10.2026): `dead_settings.py` показывал 11 мёртвых, из них **9 были живыми**.

| Ловушка | Что происходит | Как отличить |
|---|---|---|
| Ключ собирается в коде | `model_for(role)` читает `get("model_" + role)` — литерала в коде нет | Искать вызов `model_for("роль")` |
| Персональная настройка | `get_for(login, key)` читает не `config.json`, а `user_prefs.json` | Смотреть `PERSONAL_KEYS` в `settings.py` |
| Упоминание в комментарии | строка с ключом в комментарии выглядит как чтение | Только AST, не текст |
| Прочитал и выбросил | `settings.get("x")` отдельным выражением — значения нигде нет | Родитель узла — `ast.Expr` |

**Правильный инструмент:** `python dev\audit_settings.py` — разбор кода через `ast`,
уровни A (работает) · A\* (живая, но не там, где кажется) · B (только GUI) · C (мёртвая) · D (прочитал и выбросил).
Состояние дома на 04.10.2026: **C=0**.

## 2. ВТОРОЙ КЛАСС НАХОДОК: НАСТРОЙКА РАБОТАЕТ, НО ЕЁ НЕ ВИДНО

Флаг `ui=False` в `REGISTRY` прячет настройку из панели. Человек её не может тронуть —
при том, что код её читает. Проверка списка скрытых: любой прогон по `REGISTRY`, где `not ui`.
Найдено 04.10.2026: 9 скрытых, из них 6 **работали** (`chunk_size`, `chunk_overlap`,
`history_days`, `client_days`, `repo_boost_min_sim`, `vision_gpu`) — открыты в панель.

**Вывод для будущих ног:** настройку нельзя считать «сделанной», пока человек может её увидеть и поменять.

## 3. ТРЕТИЙ КЛАСС: ОБЪЯВЛЕНО, НО НИКОГДА НЕ ВЫЗЫВАЕТСЯ

`model_fast`, `model_creo`, `model_spec`, `model_web`, `model_audit` — роли есть в панели,
но `model_for("роль")` в коде **не встречается ни разу** (проверено 04.10.2026: реально
зовутся только `chat` и `trail`, плюс `vision` и `index`).
Правило: **роль модели считается живой только если есть реальный вызов `model_for("роль")`**.

## 4. ТАБЛИЦЫ-ПРИЗРАКИ: ПРОВЕРЯТЬ ФАКТОМ, А НЕ ПО КОММЕНТАРИЮ

Таблица может быть удалена, а чтение остаться. Симптом: `no such table: X`.
Проверка (одна проба, ~10 строк): `SELECT name FROM sqlite_master WHERE type='table'`.

Факты agent.sqlite на 04.10.2026 (21 таблица): `bom` — **36 811 строк (жива)**,
`links` — 0 (связи ведёт ПЛМ-READER), `usage` — **нет** (призрак), `usage_meta` — **нет** (призрак),
`files` 48 758, `models` 44 154, `history` 172, `fts_index` 7 283.

**Грабля этой волны:** `bom` выглядела призраком по карте `io_map` («только читается»),
но на деле жива. Вывод: «никто не пишет» ≠ «нет данных». Всегда сверяться с базой.

## 5. ПОРЯДОК ЛЕЧЕНИЯ (проверен)

1. Проверить наличие таблицы/функции **фактом**, не комментарием.
2. Сделать код устойчивым: проверка наличия → запасной источник → внятный текст.
3. Перезапустить агент и проверить **вживую через HTTP**, а не импортом.

## 6. ГРАБЛИ ПРОБ (главное — проба не должна врать)

- **401/404 не считать успехом.** Проба «в ответе нет слов про баг» ПРОХОДИЛА на 404
  и на 401 — то есть отказ принимался за починенное. Проверка бага обязана требовать
  **реального ответа инструмента**, иначе она ничего не проверяет.
- **Не выдумывать маршруты.** Маршрута `POST /tool` в доме **нет**: инструменты вызывает
  модель через `/ask`, витрина — своими маршрутами (`/map/data`, `/api/tools`, `/settings`).
- **Токен** — из `data\secrets.json`, маршрут `/login` (манифест п.4).
- **Проба не должна портить боевой конфиг** (было: тестовые значения остались в `config.json`).

## 8. ЧЕГО НЕ ДЕЛАТЬ

- Не объявлять настройку «мёртвой» по поиску имени.
- Не оставлять настройку скрытой (`ui=False`), если человек обязан её менять.
- Не удалять таблицы из базы без прямого слова владельца (манифест п.5) — чинить чтение.
- Не верить комментарию «таблица удалена» — верить `sqlite_master`.
