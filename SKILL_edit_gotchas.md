# ГРАБЛИ ПРАВКИ ФАЙЛОВ И КОМАНД (живые, с обходами)

> Собрано по фактам реальных сессий 15–16.10.2026. Каждая грабля стоила ходов. Читать ПЕРЕД правкой.

## 0. 🔴 САМАЯ ЧАСТАЯ: `text not found` ПРИ ТОЧНО СУЩЕСТВУЮЩЕМ ТЕКСТЕ

**Живой факт (16.10.2026, 3 попытки подряд):** правлю обряд в `law_H15.md`. Текст прочитан построчно,
скопирован «дословно» — `editor` трижды вернул `text not found`. Файл при этом **в LF, без BOM**:
```
\r\n count: 0     ← CRLF НЕТ
одиночных \n: 110 ← только LF (Unix)
BOM: 35,32,46     ← НЕТ (это '# .')
```

**Причины (все три сразу):**
1. **Файлы дома — в LF, не CRLF.** Вывод `read_files` показывает `\n`; при копировании блока
   из **многострочного** фрагмента переносы/склейка могут не совпасть → промах.
2. **Якорь ВЗЯТ ИЗ ОТОБРАЖЕНИЯ, а не из свежего чтения** (номера строк, «…», обрезка) → в тексте его нет.
3. **Якорь многострочный и длинный** — растёт вероятность одного отличия (лишний пробел, «ё»/«е»).

**ОБХОД (жёсткий порядок):**
1. `old_text` — **ОДНА строка**, короткая (≤ 120 символов), скопирована из **свежего** `read_files`.
2. **Никогда** не брать `old_text` из вывода `run_commands` (там склейка, табы, ANSI).
3. **Две неудачи подряд = СТОП.** НЕ повторять тот же якорь. Варианты по порядку:
   - сузить до **одной строки** (или до её уникального куска);
   - правка **через `run_commands`** (`-replace` по regex с `[regex]::Escape`) — для больших блоков;
   - **пересоздать файл целиком** через `editor` (когда правок много).
4. Проверка после правки: `Select-String -Pattern '<маркер>'` — правка применилась.

**Правило дома:** `editor` — для **коротких однострочных** якорей. Всё крупнее — `-replace` или пересоздание.

## 1. `editor` СОЗДАЁТ ФАЙЛ БЕЗ BOM → КИРИЛЛИЦА В `.ps1` ЛОМАЕТ ПАРСЕР

**Симптом:** после создания/правки `.ps1` через `editor`: `Непредвиденная лексема "<кириллица>"`.
**Причина:** PowerShell 5.1 без BOM читает файл как ANSI → русские буквы в мусор → парсер валится.
**Обход (всегда после создания русского `.ps1`):**
```powershell
$f='<файл.ps1>'; $t=$null;$e=$null
[void][System.Management.Automation.Language.Parser]::ParseFile($f,[ref]$t,[ref]$e)
if($e.Count -or ([IO.File]::ReadAllBytes($f))[0] -ne 0xEF){
    $txt=[IO.File]::ReadAllText($f,[Text.Encoding]::UTF8)
    [IO.File]::WriteAllText($f,$txt,(New-Object Text.UTF8Encoding($true)))   # $true = С BOM
}
```
**Правило:** русские `.ps1` после `editor` — **всегда** проверка `ParseFile` + BOM. Массовые замены — только `UTF8Encoding($true)`.

## 2. `editor` МОЖЕТ СХЛОПНУТЬ ФАЙЛ В ОДНУ СТРОКУ

**Симптом:** перезапись через `editor` (создание существующего файла заново) → весь код **в одну строку**, `\n` потеряны, `$переменные` съедены.
**Обход:** для **многострочных** файлов использовать `[IO.File]::WriteAllLines($путь, $массивСтрок, (New-Object Text.UTF8Encoding($true)))` — каждая строка отдельным элементом массива.
**Проверка:** `(Get-Content $f).Count` — если 1 при ожидаемых 40 — файл схлопнут.

## 3. КАВЫЧКИ В `-Command` / `cmd /c` → ОБРЫВ ВЫЗОВА

**Симптом:** `Непредвиденная лексема "сколько"`, `Отсутствует выражение после ","`, `Missing closing '}'`.
**Причина:** вложенные кавычки (`"..."` внутри `'...'` внутри `\"...\"`) не переживают двойную обработку PowerShell+cmd.
**Обход (по приоритету):**
1. **Файл-скрипт** вместо inline: записать `.ps1`/`.py` и запустить `-File`/путь.
2. Кириллицу и сложные строки — **не передавать через `-Command`**, только через файл.
3. Если перевод строки: `[Environment]::NewLine` или `` `n `` внутри `"..."` (double-quoted), НЕ внутри `'...'`.

## 4. `;` В POWERSHELL: ЦЕПОЧКА ПРЕРЫВАЕТСЯ НА ПЕРВОЙ ОШИБКЕ

**Симптом:** вторая команда не выполнилась (`A; B` — B не сработала).
**Причина:** `powershell.exe` возвращает код ошибки при `2>&1` от native-команды, и Cline видит «Command exited with code 1», хотя странно — цепочка продолжается, но вывод теряется.
**Обход:** **разделять команды на отдельные вызовы**; если нужна цепочка — `try { A } catch {}` + `B`; для native: `cmd /c "A 2>&1 & B"`.

## 5. ANSI-ШУМ `ollama stop` / `ollama list` → ЛОЖНАЯ «ОШИБКА»

**Симптом:** `ollama : [ANSI-последовательность] ... NativeCommandError` — команда **выполнилась успешно**, но PowerShell счёл это ошибкой.
**Обход:** `ollama stop <model> 2>$null | Out-Null` **с `$null`** или `cmd /c "ollama stop <model>"`. Результат проверять **отдельным** вызовом: `ollama ps`.
**Правило:** ANSI-шум ≠ сбой. Проверять по факту (ps/list), не по коду возврата.

## 6. `old_text` НЕ СОВПАЛ (`text not found`)

**Симптом:** правка не прошла, хотя «текст точно есть».
**Причины (по частоте):** (а) опечатка при копировании `old_text`; (б) взял из **устаревшего** чтения; (в) `\r\n` vs `\n`.
**Обход:** `old_text` — **только из свежего `read_files`**; при провале — **укоротить** якорь (1–2 строки), не угадывать; проверить опечатки посимвольно.
**Границы:** `insert_line` по номерам строк **ЗАПРЕЩЁН** законом §4 — только якорь.

## 7. РЕГУЛЯРКИ: lookbehind ПЕРЕМЕННОЙ ДЛИНЫ НЕ ПОДДЕРЖАН

**Симптом:** `Недопустимый шаблон регулярного выражения (?<!A|B)`.
**Причина:** .NET (PS 5.1) не умеет lookbehind переменной длины.
**Обход:** два последовательных `-replace` вместо одного сложного; или позитивный lookbehind фиксированной ширины `(?<=\d)` (один символ — можно).

## 8. ЯКОРЬ «ЗАГОЛОВОК» СЪЕДАЕТ РАЗДЕЛ

**Симптом:** после правки число разделов уменьшилось.
**Причина:** `old_text` = строка заголовка → она заменяется вместе с блоком, содержимое «осиротело».
**Обход:** `old_text` — **минимум две строки ПОСЛЕ заголовка** (заголовок входит в `new_text`).
**Проверка сразу:** `(Select-String -Path $f -Pattern '^## ' | Measure-Object).Count` — должно совпасть с ожидаемым.

## 9. БОЛЬШОЙ `new_text` → ТАЙМАУТ `editor`

**Симптом:** `Editor input too large` (>6 000 символов) или таймаут.
**Обход:** дробить на несколько вызовов; **создавать большие файлы частями**: пустой файл → дописывать блоками через `insert_line`/`editor`.
**Лимит дома:** блок `editor` ≤ 6 КБ (§4 `.clinerules`).

## 10. НЕОПРЕДЕЛЁННАЯ ПЕРЕМЕННАЯ = БЕЗЗВУЧНЫЙ ДЕФЕКТ (дорогой!)

**Симптом:** код работает, но результат неверный; в отчётах «пусто», флаги не срабатывают.
**Причина:** в PowerShell обращение к **неопределённой** переменной даёт `$null` **без ошибки** →
условие тихо ложно, вывод тихо пуст. Компилятор молчит.
**Живой факт (16.10.2026):** в `check_3_skills_avail.ps1` переменная `$ans` **использовалась в 3 местах**
и **нигде не задавалась** → все отчёты печатали «(пусто)», детекторы `FAKE_CALL`/`[START:` слепли.
**Правило:** после **любой** правки скрипта — проверка, что все используемые переменные определены:
```powershell
# $var — замени на имя; для скрипта проверяй КАЖДУЮ переменную из подозрительных условий
$uses = @(Select-String -Path $f -Pattern '\$var[^a-zA-Z]').Count
$defs = @(Select-String -Path $f -Pattern '\$var\s*=').Count
if ($uses -gt 0 -and $defs -eq 0) { "ДЕФЕКТ: $var не определена" }
```
**Лечение:** определить переменную **до** первого использования (обычно сразу после вызова функции).
**Общий приём:** `Set-StrictMode -Version Latest` в начале скрипта → PowerShell начнёт **ругаться**
на неопределённые переменные (ловит класс дефекта заранее).

## 11. ФАЙЛ БОЛЬШОГО РАЗМЕРА НЕ ЧИТАТЬ ЦЕЛИКОМ

**Симптом:** таймаут инструмента, окно переполнено, «дорого».
**Обход:** читать **диапазонами строк** (`start_line`/`end_line`) по якорю; искать через `Select-String`
и читать только совпавшие участки. Файлы > 40 КБ целиком — только по частям.

## 12. РЕГИСТР: PowerShell НЕ РАЗЛИЧАЕТ, PYTHON РАЗЛИЧАЕТ (живой факт 16.10.2026)

**Симптом:** строка «есть в файле» (найдена `Select-String`), но Python-код её **не находит** →
health check/чекер падает вхолостую, хотя правило на диске присутствует.

**Живой факт (16.10.2026, правка движка стенда `loop_revive_test.py`):**
пункт `RULES_REQUIRED` содержал `"ПРЕДПОЛОЖЕНИЕ"` (все буквы заглавные). В законе vG2 это
написано как **`Предположение`** (строка 28: `2.5. «Цитата: …» — из файла; «Предположение: …» — догадка.`).
Проверка `Select-String` (по умолчанию **без** `-CaseSensitive`) находила 1 совпадение —
и это создавало ложную уверенность. Но движок проверяет через Python `k in HOUSE_SYSTEM`,
а `in` для строк **ЧУВСТВИТЕЛЕН К РЕГИСТРУ** → пункт считался отсутствующим, `check_rules_health`
возвращал `False`, прогон объявлялся недействительным.

**Правило (при переносе строк PS → Python):**
1. `Select-String` в PS 5.1 по умолчанию **регистронезависим** — совпадение ≠ точная форма строки.
2. Нужна точная форма → запрашивать её **регистрозависимо**:
   ```powershell
   Select-String -Path '<файл>' -Pattern '<строка>' -CaseSensitive    # точная форма
   ```
   либо брать форму из живой цитаты `read_files` (лучший путь).
3. Python: `in`, `==`, `str.find()` — **регистрозависимы**; если нужна устойчивость —
   `.lower()` с обеих сторон (но тогда фиксируй это явно в комментарии).
4. Кириллица усугубляет: «е»/«ё», «и»/«й» — визуально похожи, а в байтах разные.

**Проверка после правки:** прогнать код и убедиться, что пункт найден (`check_rules_health: True`),
а не доверять одному `Select-String`.

## 13. `python -c` ИЗ POWERSHELL ЛОМАЕТСЯ НА КАВЫЧКАХ (живой факт 16.10.2026)

**Симптом:** `Исключение при вызове "Create" с "1" аргументами`, `Отсутствует имя типа после
знака "["`, `Непредвиденная лексема ")"`, `Непредвиденный атрибут "print"` — хотя команда выглядит верной.

**Причина:** PowerShell сам разбирает строку ДО передачи в `cmd /c`. Любые кавычки внутри
(`"`, `'`, `[`, `]`, `(`, `)`) конфликтуют с экранированием PS → питон получает обрывок кода.

**Живой факт:** `cmd /c "python -X utf8 -c "import ctx_variants as c; [print(n, len(t)) for n, t in c.cases()]""`
упал с четырьмя ошибками парсинга PS (список-компоновка + `print`).

**Правило дома (§5.1 п.2 `.clinerules`):** инлайн `python -c` **ЗАПРЕЩЁН**.
Питон — только файлом:
```powershell
# 1) создать .py через editor (кириллица — только editor/write_file)
# 2) запустить с редиректом, чтобы PS не глушил traceback
cmd /c "python -X utf8 <путь>.py > <путь>_out.txt 2>&1"
# 3) прочитать результат read_files
```
**Почему файл лучше:** кавычки не конфликтуют; `2>&1` пишет traceback в файл
(PowerShell иначе заворачивает stderr в `NativeCommandError` и **скрывает настоящую ошибку** —
та же грабля стоила двух ходов при первом запуске `stand_audit.py`).

**Уборка:** временный `.py` в `tmp\` — удалить сразу после исполнения (§5.2 п.8).

## 15. 🔴 КИРИЛЛИЦА В `old_text` НЕ МАТЧИТСЯ, ЕСЛИ ВЗЯТА ИЗ ОТОБРАЖЕНИЯ (23.10.2026, 3 промаха)

**Симптом:** `editor` → `No replacement performed: text not found` — при том, что строка ВИДНА в файле.
Word-структура в отображении: `РџРћР”РЎР§` (мохибейк), а файл при этом **UTF-8/BOM или без**.

**Живой факт (23.10.2026):** правил карту `SKILL_index.md` — якорь с «ПОДСЧЁТ» не матчился 3 раза.
Причина не в кодировке файла (UTF-8 + BOM `239,187,191`), а в том, что **текст якоря был взят из
усечённого вывода** `run_commands`, где кириллица шла мохибейком (`РџРћР”РЎР§`). В файле — нормальные
UTF-8 байты. Итог: якорь физически не равен содержимому.

**ОБХОД (порядок жёсткий):**
1. `old_text` — **только из свежего `read_files`**, НЕ из `run_commands` и НЕ из «я вижу в выводе».
2. Якорь с кириллицей не матчится 1 раз → **сразу перейти на ЛАТИНСКИЙ якорь** (имя файла,
   `SKILL_`, бэктики, `Prog\`, цифры). Пример: вместо «ПОДСЧЁТ ФАЙЛОВ» брать `SKILL_count_files_template.md`.
3. Проверить уникальность якоря **до** правки:
   ```powershell
   $t=[IO.File]::ReadAllLines($p,[Text.Encoding]::UTF8); ($t|Select-String -SimpleMatch '<якорь>'|Measure-Object).Count
   ```
   Нужно ровно `1`.
4. 2 промаха подряд → **смена метода** (§5.1): Python-скрипт с `io.open(..., encoding="utf-8-sig")`,
   правка строки **по индексу** в массиве строк, а не по подстроке.

**ГРАБЛЯ ВНУТРИ ГРАБЛИ (поймана тут же):** правка ФРАГМЕНТА строки через `editor` **не удаляет**
остаток строки — получается обрубок: `- **ПОДСЧЁТ …:** - **ЭСТАФЕТА …`. Якорь обязан либо покрывать
ВСЮ строку, либо быть точным фрагментом, а остаток удалять отдельно. Проверка после правки —
печать изменённых строк (`ReadAllLines` + индексы), а не доверие diff'у.

## 16. СКРИПТ-ПИСАТЕЛЬ РОНЯЕТ CRLF → ВЕСЬ ФАЙЛ «ИЗМЕНЁН» (23.10.2026)

**Симптом:** `git diff --numstat` показывает `253 253` (весь файл), хотя правил **6 строк**.
История засоряется «переписыванием» файла.

**Причина:** `io.open(P, "w", encoding="utf-8-sig", newline="")` + `"\n".join(lines)` — пишет **только LF**,
а файл дома был **CRLF**. git считает каждую строку изменённой.

**Живой факт:** `SKILL_index.md` — было `CRLF=248`, стало `CRLF=0`; коммит унёс 501 строку вместо 6.

**ОБХОД:**
1. Перед правкой — замерить EOL: `$b=[IO.File]::ReadAllBytes($p); ($b|?{$_ -eq 13}|Measure-Object).Count`.
2. Писать **тем же** EOL, что был: читать с `newline=""`, **не** нормализовать, либо явно
   `data.replace("\r\n","\n").replace("\n","\r\n")` перед записью.
3. **После правки — проверить счётчик CR** и `git diff --numstat` **до** `git add`.
4. Поймал регресс после коммита → вернуть CRLF и `git commit --amend --no-edit -- <paths>`
   (amend — тоже с pathspec, §SKILL_parallel_legs).

## 17. «TEXT NOT FOUND» ПОСЛЕ УДАЧНОЙ ПРАВКИ = ПРАВКА УЖЕ ПРИМЕНЕНА (23.10.2026)

**Симптом:** второй `editor` с тем же `old_text` возвращает `text not found`, хотя файл только что
правился именно так.

**Причина:** первая правка УЖЕ заменила якорь. Повтор ищет то, чего больше нет → это **не** промах,
а сигнал «готово».

**Правило:** прежде чем менять метод — **прочитать файл** и убедиться, какая форма сейчас на диске
(§М.2д: повтор без изменений = СТОП, меняй метод, а не количество попыток).

## 18. 🔴 ФУНКЦИЯ «ЧТЕНИЕ» МОЖЕТ ПИСАТЬ — ПРОБА ИСПОРТИЛА ЖИВЫЕ НАСТРОЙКИ (23.10.2026)

**Симптом:** после «безопасной» пробы настройки приложения изменились сами.
**Живой факт (PLM Reader):** проба звала `plm_settings.load_settings_file(path=<копия в песочнице>)`.
Функция **кроме чтения** делает подчистку и перенос старых файлов (стр. 240–246), поэтому
**живой `settings\settings.json` был перезаписан тестовыми данными** (`folders="Z:\A; Z:\B"`).
Живое окно подтвердило: «Папок скана: 6: Z:\; Z:\A; Z:\B».

**ПРАВИЛО (жёсткое):**
1. Перед вызовом чужой функции — **прочитать её тело** (не имя!) и найти `open(...,"w")`,
   `os.replace`, `shutil.move`, `os.remove`, `_archive_*`, `save_*`. Есть — это **пишущая** функция.
2. Для проб проверки: **не запускать программу в рабочем каталоге**. Копия каталога в песочницу
   (`%TEMP%` или `log\urn\<исполнитель>\sandbox\<метка>\`) — и работать там.
3. Пробы на «битый файл/миграции» — только над **копией**, при этом функция должна зваться так,
   чтобы её побочные действия били по песочнице (`SETTINGS_DIR` внутри песочницы), а не по живому.
4. Перед пишущей пробой — **снимок живого файла** (`Copy-Item <файл> <урна>\<файл>_before`),
   чтобы откат был мгновенным.
5. Признак, что уже навредил: изменился `LastWriteTime` живого файла, появился новый файл в
   `backup_settings\` / `db\backup\`, изменились данные на экране.

**Восстановление (проверено):** найти **полный** бэкап среди ротационных копий (не огрызок:
смотреть размер!), вернуть нужные ключи, записать, **перезапустить программу и подтвердить
скриншотом**. Огрызки (десятки байт) — это не бэкапы, а мусорные записи.

## 19. 🔴 ТРИ ПРИЗРАКА СВЯЗЕЙ: связи «есть», а их НЕТ (23.10.2026, PLM Reader)

**Симптом:** узел показывает «состав 0 · входит 0», в графе — одинокая вершина. Пользователь говорит
«связи не работают», хотя в базе связи **лежат**.

**Живые факты (база plm_reader, 23.10.2026):**
| Модель | Что в базе | Почему «нет связей» |
|---|---|---|
| `170META-1-02-ЯЩИК-НИЗ-ЛИТНИК` (MFG) | `links: 1` → **`SBORKA_MFG`** (qty=31) | связь ведёт в **служебный шаблон**, а шаблоны **вырезаются** фильтром (`plm_graph.py:545`) → оба конца обрезаны |
| `170META-1-02-ЯЩИК-НИЗ-ЛИТНИК_Z` | `links: 0`, `derived: 0` | связь `inherit_from_master` (мастер-модель) **не собрана движком вообще** |
| `127_53_00_BODY-MFG`, `EF8-5_10_02_01` | `links: 0` | роль MFG/ЧПУ: состав **не разбирается** (`setup_data` в файлах отсутствует) |

**ТРИ ПРИЗРАКА (проверять всегда):**
1. **Связь-в-шаблон.** `parent`/`child` = `SBORKA_MM`, `SBORKA_MFG`, `MM_PART`, `MFG_NC` → это **не связь
   изделия**, а шаблон. Если фильтр шаблонов включён — узел останется одиноким. **Считать такие связи
   отдельно** и не выдавать за «нет данных».
2. **Связь не собрана движком.** «Нет в `links`» ≠ «нет в файле». Тип связи может просто **не читаться**
   (мастер-модель по `Base_Part`/`_Z`, сознание ЧПУ по `T0xxx`/операциям).
3. **Обрезка лимитом.** `total > 120` / `slice(0,25)` в обходе **съедают** связи ещё до показа.

**КЛАСС ГРАБЛИ (общий, не только PLM):** прежде чем говорить «данных нет», проверь,
**не отфильтрованы/не обрезаны** ли они на входе. «Пусто на экране» ≠ «пусто в базе».

**Как проверять (SQL, живым счётом):**
```sql
-- что вообще есть у модели
SELECT parent, child, qty FROM links WHERE parent=? OR child=?;
SELECT child, base, kind  FROM derived WHERE child=? OR base=?;
-- общая заполненность (2026-10-23: links 24 877; parent-уник 15 897; child-уник 8 187 из 46 756 моделей)
SELECT COUNT(*), COUNT(DISTINCT parent), COUNT(DISTINCT child) FROM links;
```

## 20. 🔴 ТИП КЛЮЧА В JS: JSON ПРЕВРАЩАЕТ ЧИСЛА В СТРОКИ → ГРАФ ПУСТ (23.10.2026)

**Симптом:** SVG нарисован, но **пуст** (`SVG0|ND0|P0`), **ошибок в консоли НЕТ**, приёмка зелёная.
**Живой факт (PDM-Консоль):** граф был мёртв **всегда**, три причины одной семьи:

| # | Код | Что ломалось |
|---|---|---|
| 1 | `Object.keys(rows).map(Number).sort(...)` | ключи `rows` — СТРОКИ (`"0"`), после `Number` — числа → `rows[0]` = `undefined` → `rows[c].sort()` **TypeError** |
| 2 | `const nm = t[0]` (индекс из `links`) | в данных индекс — **число**, ключи объекта — **строки** → `ND[0]` ≠ `ND["0"]` → обход падал |
| 3 | `for (const m of Object.keys(pos))` → `ND[m]` | ключ мог быть числом → `n = undefined` → `n.m` **TypeError** |

**ПРАВИЛО:** в JS **любой ключ объекта** после JSON — **строка**. Приходящие из данных **числовые индексы**
приводить **сразу**: `String(t[0])`. И **защищаться**: `if (!n) continue;` перед работой с узлом.

**ПОЧЕМУ НЕ ВИДНО:** исключение внутри `show()`/`draw()` не всплывает наверх → консоль чистая → «всё ок».
**ЛОВИТЬ ТАК (рабочий метод, проверено):** дописать в конец HTML зонд, который зовёт функцию и пишет
результат в `document.title`/`<div id="__audit">`, затем
`chrome --headless=new --dump-dom <page>` → прочитать хвост DOM. Даёт **точную строку падения**:
```
show ERR: TypeError: Cannot read properties of undefined (reading 'm')
    at draw (page.html:317:43)      ← вот искомая строка
```

## ПРОБА
Назвать: (1) что делать после создания русского `.ps1` через `editor` → **проверить BOM+ParseFile**;
(2) почему `A; B` может терять B → **код возврата/вывод**; (3) чем писать многострочный файл → **WriteAllLines**;

## 14. КИРИЛЛИЦА В `print()` (encoding crash)

**Симптом:** При выводе кириллических строк через `print()` в Windows-консоль (PowerShell/CMD), вместо текста отображаются `�` (encoding mismatch).

**Причина:** Консоль по умолчанию использует ANSI/OEM кодировку, а Python выводит UTF-8. Это не ломает логику, но делает отчет нечитаемым.

**Обход:**
1. Для отчетов и логов: выводите результат в файл `> out.txt 2>&1` и читайте через `Get-Content -Encoding utf8`.
2. Для визуального контроля: используйте английский (ASCII) в ключевых `print()`-ах, если планируете смотреть в консоль.
3. Для проверки: используйте `Select-String` или `Get-Content` для верификации содержимого.
